## 1. Что такое OpenStreetMap

### 1.1. Определение

**OpenStreetMap (OSM)** — открытая географическая база данных, которую совместно создаёт и обновляет сообщество участников. В ней описываются дороги, тропы, здания, водоёмы, адреса и другие объекты. Данные можно использовать для собственных карт и приложений с соблюдением лицензии.

Участник добавляет сведения об объектах, их расположении и свойствах. Пользователь данных решает, как их отображать, анализировать и преобразовывать. Поэтому из одной OSM-выгрузки могут получаться разные продукты: автомобильная карта, пешеходная схема, анализ доступности или граф доставки.

Источник: [официальное введение What is OpenStreetMap?](https://welcome.openstreetmap.org/what-is-openstreetmap/).

### 1.2. Что необходимо различать

| Сущность | Что содержит | Роль в курсовой |
|---|---|---|
| База OSM | Географические объекты, связи и теги | Источник дорожной сети |
| Файл `.osm.pbf` / `.osm` | Выгрузку объектов OSM | Зафиксированный вход эксперимента |
| Карта на экране | Визуальное представление данных | Проверка расположения объектов |
| Растровый тайл | Уже нарисованный фрагмент карты | Подложка для иллюстрации |
| Дорожный граф | Структуру связности и стоимости движения | Вход алгоритма поиска пути |
| Маршрутизатор | Программу импорта, поиска и выдачи маршрутов | Средство проведения экспериментов |

**Эта таблица задаёт терминологию исследования.** Например, изображение улицы на подложке не даёт ни её идентификатора, ни списка узлов, ни правил доступа. Для вычислений нужны исходные геоданные или производный граф.

### 1.3. Где данные полезны

Для темы курсовой особенно важны следующие направления применения:

- **Навигация:** нахождение маршрутов для выбранного транспорта.
- **Логистика:** оценка путей между точками доставки и территориальных ограничений.
- **Городской анализ:** связность сети, доступность районов, последствия перекрытий.
- **Геоинформационные системы:** совместный анализ дорог и площадных объектов.
- **Исследования:** воспроизводимые сравнения методов на открытых исходных данных.

Это примеры задач, которые можно поставить на дорожном графе. Сам факт наличия дороги в OSM ещё не гарантирует достаточность её атрибутов для каждого приложения.

## 2. Почему OSM подходит для этой курсовой

В исследовании нужно связывать геометрию дорог с весовыми полигонами. У OSM есть подходящая для этого основа: положения точек, порядок точек в линиях, описательные теги и отношения между объектами. На этой основе можно построить сеть и сохранить происхождение каждого участка.

Но OSM не задаёт готовую универсальную стоимость движения. Она получается после выбора транспорта и правил обработки. Например, один профиль исключит лестницы из автомобильного графа, другой включит их в пешеходный. Применение пользовательских зон — ещё один слой модели поверх такой сети.

**Следствие для эксперимента:** сравнивать методы наложения полигонов следует на одном снимке OSM, одном транспортном профиле и одной исходной модели стоимости. Иначе различия маршрутов нельзя уверенно отнести к исследуемому методу.

## 3. Основные объекты OSM

### 3.1. Три вида элементов и теги

Базовая модель включает:

- `node` — точку с координатами;
- `way` — упорядоченный список ссылок на узлы;
- `relation` — объединение элементов с заданными ролями.

Свойства записываются тегами `ключ=значение`. Теги могут принадлежать каждому из трёх видов объектов. Отдельного базового элемента «ребро маршрутизатора» в этой модели нет: его создаёт потребитель данных.

Источник: [OSM Wiki — Elements](https://wiki.openstreetmap.org/wiki/Elements).

### 3.2. Node: узел исходных данных

Узел имеет идентификатор, широту и долготу. В дорожной линии он может задавать изгиб, пересечение, конец дороги или объект со своими свойствами. Поэтому **OSM node не всегда является перекрёстком**.

Учебный пример:

```xml
<node id="101" lat="55.7500" lon="37.6100" />
<node id="102" lat="55.7505" lon="37.6110">
  <tag k="highway" v="traffic_signals" />
</node>
```

Здесь первый узел только задаёт положение, второй дополнительно помечен как светофор. Координаты и идентификаторы условные; это не ссылка на реальные объекты.

При упрощении графа важно учитывать свойства (теги) узла. Иначе промежуточная точка со значимым ограничением может исчезнуть вместе с информацией, которую необходимо учитывать.

Источник модели узла: [OSM Wiki — Node](https://wiki.openstreetmap.org/wiki/Node).

### 3.3. Way: линия как последовательность ссылок

Пример линии:

```xml
<way id="1001">
  <nd ref="101" />
  <nd ref="102" />
  <nd ref="103" />
  <tag k="highway" v="residential" />
  <tag k="oneway" v="yes" />
</way>
```

Way хранит порядок `101 → 102 → 103`, а координаты берутся из соответствующих nodes. Поэтому выгрузка с way, но без нужных узлов недостаточна для восстановления линии.

Одна улица может состоять из нескольких ways: например, после изменения свойств или в местах разбиения. В обратную сторону тоже нет равенства «один way = одно ребро»: way может содержать несколько перекрёстков и порождать несколько участков графа.

Замыкание линии не превращает её автоматически в площадь. Кольцевая дорога может оставаться линейным объектом, а граница здания — описывать площадной. Смысл определяется тегами и контекстом.

Источник: [OSM Wiki — Way](https://wiki.openstreetmap.org/wiki/Way).

### 3.4. Relation: связь между объектами

Для дорожной задачи наиболее важны отношения ограничений поворота. Типичная restriction relation связывает:

- `from` — дорогу, с которой въезжают;
- `via` — узел или последовательность дорог, через которые проходят;
- `to` — дорогу, на которую выезжают.

Значения `no_*` запрещают манёвр, `only_*` ограничивают набор разрешённых манёвров. Возможны исключения для транспорта и условные ограничения.

```xml
<relation id="5001">
  <member type="way" ref="1001" role="from" />
  <member type="node" ref="103" role="via" />
  <member type="way" ref="1002" role="to" />
  <tag k="type" v="restriction" />
  <tag k="restriction" v="no_left_turn" />
</relation>
```

Все ссылки здесь учебные; для полного OSM-файла нужны и сами объекты. Пример показывает структуру, а не геометрическую проверку левого поворота.

Источник: [OSM Wiki — Relation:restriction](https://wiki.openstreetmap.org/wiki/Relation:restriction).

### 3.5. OSM multipolygon и GeoJSON MultiPolygon

OSM-отношение `type=multipolygon` собирает площадной объект из ways с ролями `outer` и `inner`. GeoJSON `MultiPolygon` — уже геометрическое представление набора полигонов. Переход между ними требует сборки геометрии.

Пользовательские штрафные зоны не обязаны быть OSM-отношениями: достаточно независимого GeoJSON, который сопоставляется с дорожными линиями. Так сохраняются исходная сеть и сценарные изменения.

Источники: [OSM multipolygon](https://wiki.openstreetmap.org/wiki/Relation:multipolygon), [RFC 7946, геометрические объекты](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1).

## 4. Какие теги определяют дорожную сеть

Общий пример:

```xml
<!-- Жилая дорога, проезд автомобилей запрещён -->
<way id="1001">
  <nd ref="101" />
  <nd ref="102" />
  <tag k="highway" v="residential" />
  <tag k="motor_vehicle" v="no" />
</way>



<!-- Это дорога в жилой застройке с асфальтовым покрытием. 
Движение моторного транспорта разрешено только в направлении 101 → 102 → 103. 
Ограничение скорости — 40 км/ч.  -->

<way id="1001">
  <nd ref="101" />
  <nd ref="102" />
  <nd ref="103" />

  <tag k="highway" v="residential" />
  <tag k="oneway" v="yes" />
  <tag k="motor_vehicle" v="yes" />
  <tag k="maxspeed" v="40" />
  <tag k="surface" v="asphalt" />
</way>
```

### 4.1. Класс дороги: `highway`

Ключ `highway=*` используется для описания дорог и связанных объектов. Его значение у дорожного way отражает роль в сети; оно не заменяет проверку покрытия и допуска транспорта.

| Значение / группа | Краткое назначение |
|---|---|
| `motorway`, `trunk` | Крупные магистральные дороги |
| `primary`, `secondary`, `tertiary` | Последовательные уровни значимости |
| `*_link` | Соединительные участки и съезды |
| `unclassified` | Дороги низшего уровня сквозной сети; не «неизвестный класс» |
| `residential` | Дороги, обслуживающие жилую застройку |
| `service` | Подъезды и обслуживающие проезды |
| `living_street` | Улицы с особым режимом совместного использования |
| `track`, `path`, `footway`, `cycleway`, `steps` | Пути, применимость которых зависит от профиля |

Нельзя выбирать автомобильную сеть лишь условием «есть любой `highway`»: в данные попадут и пешеходные объекты, и точки вроде светофоров. Фильтр должен учитывать тип OSM-объекта, класс и доступ.

Источник: [OSM Wiki — Key:highway](https://wiki.openstreetmap.org/wiki/Key:highway).

### 4.2. Направление движения: `oneway`

Для обычной автомобильной дороги:

| Тег | Интерпретация относительно порядка nodes |
|---|---|
| `oneway=yes` | Движение вперёд по way |
| `oneway=-1` | Движение против порядка way |
| `oneway=no` | Сам тег не запрещает оба направления |

Отсутствие `oneway` не позволяет механически заключить, что дорога двусторонняя: импортёр учитывает также неявные правила и свойства вроде `junction=roundabout`. Есть исключения по видам транспорта и меняющиеся направления; их поддержку следует проверять у выбранного профиля.

Направление геометрии и разрешённое движение — разные сведения. При `oneway=-1` исходный порядок узлов не меняется, а разрешённая дуга графа создаётся в противоположную сторону. Для велосипеда и пешехода правила могут отличаться от автомобильных.

Источник: [OSM Wiki — Key:oneway](https://wiki.openstreetmap.org/wiki/Key:oneway).

### 4.3. Доступ: `access` и транспортные уточнения

Теги доступа образуют иерархию: от общего `access` до `vehicle`, `motor_vehicle`, `motorcar`, а также отдельных `bicycle`, `foot` и других классов. Более конкретное применимое правило может уточнять общее. Помимо запрета `no` встречаются `private`, `destination`, `delivery` и другие значения с различной семантикой.

Например, `access=no` вместе с `foot=yes` не следует превращать в общий запрет для пешеходов. `motor_vehicle=destination` не равно свободному транзиту и не равно безусловному запрету: доступ связан с назначением поездки.

Отсутствующие теги дополняются правилами профиля и контекстом территории. Универсального правила «нет `access` — можно всем» для импорта недостаточно.

Источники: [Key:access](https://wiki.openstreetmap.org/wiki/Key:access), [оговорки о значениях доступа по умолчанию](https://wiki.openstreetmap.org/wiki/OSM_tags_for_routing/Access_restrictions).

### 4.4. Ограничение и расчётная скорость

`maxspeed` описывает ограничение скорости, а не измеренную среднюю скорость поездки. Числовое значение без единицы обычно задаётся в км/ч; встречаются явные единицы, символические и условные значения. Также возможны `maxspeed:forward` и `maxspeed:backward`.

Для эксперимента лучше хранить отдельно:

```text
maxspeed_raw       исходная строка OSM
speed_kph          скорость, принятая моделью стенда
speed_source       parsed_tag / profile_default / другое обоснование
travel_time_s      расчётное время по принятой скорости
```

Если распознать значение не удалось, нельзя молча записывать ноль или считать строку числом. Нужны отдельное правило и запись в отчёте подготовки.

Источник: [OSM Wiki — Key:maxspeed](https://wiki.openstreetmap.org/wiki/Key:maxspeed).

### 4.5. Покрытие, барьеры и другие свойства

`surface` описывает материал покрытия, а не разрешение движения. Его удобно хранить как исходный категориальный атрибут и интерпретировать через выбранный транспортный профиль. Источник: [Key:surface](https://wiki.openstreetmap.org/wiki/Key:surface).

Барьеры могут быть точечными объектами на дороге. Наличие линии с автомобильным классом ещё не означает возможность проехать через соответствующий узел. Для собственного импортёра нужно отдельно обрабатывать `barrier` и связанные правила доступа. Источник: [Key:barrier](https://wiki.openstreetmap.org/wiki/Key:barrier).

Для расширенного профиля могут потребоваться дополнительные характеристики: `lanes`, `service`, `toll`, параметры допустимых габаритов и массы. 

### 4.6. Условные ограничения

Теги вида `access:conditional`, `maxspeed:conditional`, `restriction:conditional` задают действие при определённых условиях. Это нельзя свести к одному постоянному числу без выбора момента и правил интерпретации.

Для первого статического стенда предлагается зафиксировать одно из двух решений:

1. Вычислять поддерживаемые условия для заданного времени и документировать неподдерживаемые.
2. Исследовать упрощённую статическую модель, сохраняя условия как исходные строки и явно указывая, что они не вычисляются.

Второе решение допустимо как ограничение учебного эксперимента, но такой граф нельзя представлять как полностью корректную автомобильную навигацию.

Источник синтаксиса: [OSM Wiki — Conditional restrictions](https://wiki.openstreetmap.org/wiki/Conditional_restrictions).

## 5. Связность, мосты и тоннели

### 5.1. Пересечение линий на рисунке не создаёт перекрёсток

Рассмотрим две дороги, пересекающиеся в проекции на плоскость:

```text
         C
         |
A -------+------- B
         |
         D
```

Возможны разные модели:

- общий OSM node в списках обеих дорог — топологическая связь-кандидат;
- одна дорога проходит над другой, общей точки в данных нет — прямого перехода нет;
- дороги геометрически сближены из-за ошибки данных — требуется проверка.

Создавать общую вершину во всех геометрических пересечениях нельзя. Даже общая точка сети ещё не означает разрешение любого поворота: доступные переходы ограничиваются профилем и restriction relations.

Такое разделение геометрии и связности используется и в модели OSMnx. Источник: [OSMnx — Modeling a Network](https://osmnx.readthedocs.io/en/stable/getting-started.html#modeling-a-network).

### 5.2. Что дают `bridge`, `tunnel`, `layer`

`bridge` и `tunnel` описывают соответствующий способ прохождения участка, а `layer` — относительное вертикальное положение объектов. Значение `layer` не является высотой в метрах. Его недостаточно для полноценного трёхмерного анализа; отсутствие тега также не доказывает, что дорога лежит на поверхности.

Источники: [Key:bridge](https://wiki.openstreetmap.org/wiki/Key:bridge), [Key:tunnel](https://wiki.openstreetmap.org/wiki/Key:tunnel), [Key:layer](https://wiki.openstreetmap.org/wiki/Key:layer).

**Применение к исследованию:** зона ремонта наземного проезда и экологическая зона могут по-разному действовать на проходящий над ними мост. Поэтому правило «учитывать все уровни» или «применять только к выбранным участкам» должно быть частью сценария, а не случайным последствием двумерного пересечения.

Полигон сам по себе не сообщает, к какому уровню относится ограничение. Если у зоны таких сведений нет, стенд должен использовать зафиксированное упрощение и указывать его в результатах.

## 6. Как из OSM получается дорожный граф

### 6.1. Определение графа для работы

Предлагаемая математическая модель — ориентированный мультиграф:

```text
G = (V, E)
V — вершины сети
E — направленные рёбра движения
e = (u, v, k) — ребро с ключом k между u и v
```

Направленность нужна для одностороннего движения и различающихся стоимостей по направлениям. Несколько рёбер между одними вершинами нужны, чтобы сохранить альтернативные проезды. Такая структура поддерживается, например, классом `MultiDiGraph` в NetworkX. Источник: [NetworkX — MultiDiGraph](https://networkx.org/documentation/stable/reference/classes/multidigraph.html).

Модель графа выбирается в исследовании; она не хранится в таком виде внутри OSM.

### 6.2. Три уровня дорожного участка

| Уровень | Идентификация в стенде | Зачем нужен |
|---|---|---|
| OSM way | `osm_way_id` в конкретном снимке | Связь с источником и тегами |
| Элементарный сегмент way | `snapshot_id + way_id + segment_index` | Геометрия между соседними nodes |
| Routing edge | `graph_version + edge_id` или `(u,v,k)` | Единица работы алгоритма поиска |

Индекс сегмента нужен потому, что одной пары узлов недостаточно для всех повторений и направлений. После упрощения одно routing edge может покрывать несколько элементарных сегментов; для обратной дуги появляется ещё одно представление движения по той же линии.

**Предлагаемое правило:** сохранять таблицу соответствия `routing_edge → ordered source segments`. Это позволяет объяснить, почему полигон затронул конкретное ребро и как оно связано с исходной OSM.

### 6.3. Построение графа без упрощения

В этом варианте каждый узел дорожного way становится вершиной графа, а участок между двумя соседними узлами — ребром.

Например, way содержит четыре узла:

```text
A → p1 → p2 → B
```

Из него получаются три ребра:

```text
A → p1
p1 → p2
p2 → B
```

Направления рёбер зависят от правил движения: для двусторонней дороги добавляются и обратные рёбра.

При построении графа нужно:

1. Получить координаты узлов и прочитать их теги.
2. Соединить соседние узлы участками дороги.
3. Проверить, в каких направлениях разрешено движение.
4. Записать для каждого ребра длину, свойства дороги и стоимость проезда.
5. Отдельно сохранить ограничения поворотов: они определяют, с какого ребра на какое можно перейти.

**Преимущество:** легко проследить связь графа с исходными данными OSM.  
**Недостаток:** граф содержит много точек, которые нужны только для изображения изгибов дороги.

Если координаты какого-то узла отсутствуют, восстановить участок корректно нельзя. Такой случай нужно записать как ошибку данных.

### 6.4. Построение графа с упрощением

Упрощение уменьшает число вершин и рёбер. Промежуточные точки, которые только задают форму дороги, убираются из структуры графа.

Например:

```text
Без упрощения:  A → p1 → p2 → B   — три ребра
С упрощением:   A ─────────→ B    — одно ребро
```

При этом **форма дороги сохраняется**: новое ребро проходит через координаты `A, p1, p2, B`, повторяя исходную ломаную.

Таким образом, точки `p1` и `p2` перестают быть отдельными вершинами графа, но остаются частью геометрии ребра.

**Почему это важно для полигонов:** если заменить извилистую дорогу прямой между A и B, можно ошибочно решить, что дорога пересекает зону или объезжает её.

Объединять участки нужно с учётом их свойств:

- перекрёстки и точки со значимыми ограничениями необходимо сохранять;
- изменения доступа, скорости и других важных атрибутов нельзя терять;
- длина объединённого ребра равна сумме длин участков;
- время проезда равно сумме времён участков.

Например, если проезд трёх участков занимает 10, 15 и 5 секунд, время нового ребра составит 30 секунд.

**Преимущество:** граф становится меньше, и поиск маршрута может выполняться быстрее.  
**Главное условие:** упрощение должно сохранять форму дороги, разрешённые движения и корректную стоимость проезда.

### 6.5. Почему повороты требуют отдельной модели

Предположим, дуги `A → X` и `X → B` разрешены, но манёвр с первой на вторую запрещён. Удалить `X → B` нельзя: на неё может быть разрешён въезд с другой дороги.

Возможные решения:

- хранить разрешённые переходы и учитывать предыдущее ребро при поиске;
- использовать граф состояний, где состояние включает входящее ребро;
- поручить интерпретацию ограничений выбранному движку маршрутизации.

Обычный поиск только по вершине X не различает, откуда в неё приехали. Поэтому простой граф с длинами полезен для геометрической части исследования, но его ограничения необходимо назвать до сравнения с полноценным маршрутизатором.

Вариант с `via-way` может требовать отслеживания последовательности рёбер, а не только одного поворота. Этот случай стоит выделить в самостоятельную проверку импортёра.

## 7. Вес ребра: что именно минимизирует маршрут

### 7.1. Три разных показателя

Для каждого направленного ребра предлагается различать:

| Поле | Смысл | Единица |
|---|---|---|
| `length_m` | Длина полной дорожной геометрии | метры |
| `travel_time_s` | Модельное время проезда | секунды |
| `base_cost`, `scenario_cost` | Целевая стоимость поиска | определена моделью |

Если полигон добавляет штраф к стоимости маршрута, это не обязательно означает, что поездка займёт больше времени. Штраф может просто обозначать нежелательность проезда через эту территорию.

### 7.2. Базовые формулы

При постоянной скорости на ребре:

```text
t(e) = length_m(e) / (speed_kph(e) / 3.6) (в секундах)
```

Для минимизации длины берут `c₀(e)=length_m(e)`, для времени — `c₀(e)=t(e)`. Если скорость меняется внутри ребра, время вычисляют по участкам и суммируют.

Для пути `P` с поворотными затратами:

```text
C(P) = Σ c(e) + Σ turn_cost(e_previous, e_next)
```

### 7.3. Учебный численный пример

Длина ребра — 300 м, модельная скорость — 36 км/ч. Тогда базовое время равно 30 с. В полигоне лежит 90 м, то есть 30% линии. Пусть множитель стоимости внутри зоны равен 2, а вне её — 1.

```text
outside_time = 210 / 10 = 21 с
inside_time  =  90 / 10 =  9 с
scenario_cost = 21 × 1 + 9 × 2 = 39 условных секунд
```

Это пример пропорционального штрафа стоимости. Физическое время остаётся 30 с, если модель скорости не менялась. При штрафе всему ребру стоимость стала бы 60. При трактовке множителя как реального замедления потребуется отдельно обновить модель времени.

### 7.4. Отрицательная корректировка и отрицательное ребро

Территория может быть предпочтительной: множитель `0.8` уменьшает стоимость, сохраняя её положительной. Это не то же самое, что отрицательный вес ребра.

Для базового стенда предлагается ограничить все конечные стоимости снизу положительным `ε`. Строгий запрет реализовать исключением ребра из допустимого поиска, а не произвольным «огромным штрафом». Иначе при отсутствии альтернативы алгоритм всё равно может выбрать запрещённую дорогу.

Дейкстра применяется при неотрицательных весах. Для A* дополнительно нужна допустимая эвристика. Если веса уменьшаются относительно базового графа, прежняя оценка оставшейся стоимости может завысить действительную. Безопасный проверочный вариант — `h=0`, то есть поиск Дейкстры.

Источник по алгоритму и интерфейсу: [NetworkX — dijkstra_path](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.shortest_paths.weighted.dijkstra_path.html). Ограничение на множители и использование `ε` — предлагаемое решение стенда.

## 8. Координаты, геометрия и длина

Справка терминов: 

CRS — система координат
WGS 84 — географическая система, используемая для координат OSM.
EPSG:3857, или Web Mercator — проекция, часто используемая для отображения веб-карт; расстояния в ней искажены.
geometry и geography — типы пространственных данных PostGIS: первый используется для плоских вычислений в заданной CRS, второй — для расчётов на поверхности Земли.
Буфер — область на заданном расстоянии вокруг объекта, например полоса шириной 10 метров вокруг дороги.

### 8.1. Где координаты, а где метры

Координаты OSM nodes задаются широтой и долготой на WGS 84. В GeoJSON позиция записывается в порядке `[долгота, широта]`. У API и функций порядок параметров может отличаться, поэтому для каждого интерфейса его нужно проверить отдельно.

Источники: [OSM Node](https://wiki.openstreetmap.org/wiki/Node), [RFC 7946, Position](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.1).

Для работы предлагается хранить две формы геометрии:

- исходную WGS 84 — для обмена и связи с картой;
- рабочую в подходящей локальной метрической проекции — для длины, буферов и наложений.

Для расчёта геодезических длин возможен и тип `geography`. В PostGIS единицы длины `geometry` зависят от CRS, а `geography` возвращает длину в метрах. Источник: [PostGIS — ST_Length](https://postgis.net/docs/ST_Length.html).

### 8.2. Почему недостаточно указать EPSG:3857

Наличие метров в единицах проекции не означает отсутствие искажений масштаба. Для локального сравнения нужны обоснованный выбор рабочей CRS и одинаковый способ вычисления полной длины и длины пересечения. Менять CRS между методами нельзя, если исследуется влияние самого метода сопоставления.

Необходимо различать назначение CRS и преобразование координат: простая замена метки системы не пересчитывает числа. В отчёте следует указать исходную и рабочую CRS, способ преобразования и единицы результатов.

**Уточнение к терминологии проекта:** WGS 84 относится к исходным координатам OSM; Web Mercator обычно относится к картографическому отображению. Называть EPSG:3857 «системой исходных данных OSM» некорректно.

### 8.3. Геометрия ребра важнее прямой между концами

Даже после удаления промежуточных вершин из топологии их координаты должны оставаться в геометрии. Длина хорды и длина ломаной могут различаться; пересечения с зоной — тоже. В пространственных проверках следует использовать полную линию движения, а не отрезок между вершинами графа по умолчанию.

## 9. Форматы и способы получения данных

### 9.1. Сравнение представлений

| Представление | Для чего удобно | Что проверить |
|---|---|---|
| OSM XML `.osm` | Читать небольшие учебные примеры | Наличие ссылочных объектов |
| OSM PBF `.osm.pbf` | Хранить и обрабатывать региональный снимок | Полнота и дата набора |
| Overpass JSON | Изучать выбранные объекты по запросу | Это формат ответа OSM API, не GeoJSON |
| GeoJSON | Передавать готовые геометрии и свойства | Сохранены ли OSM IDs и нужные связи |
| GraphML | Сохранять граф и его атрибуты | Совместимость типов при загрузке |

XML и PBF представляют модель объектов OSM разными способами. Преобразование в геометрический формат требует разрешить ссылки nodes → ways; оно само по себе не создаёт маршрутизационную модель.

Источники: [OSM XML](https://wiki.openstreetmap.org/wiki/OSM_XML), [PBF Format](https://wiki.openstreetmap.org/wiki/PBF_Format), [Pyosmium — Working with Geometries](https://docs.osmcode.org/pyosmium/latest/user_manual/03-Working-with-Geometries/).

### 9.2. Откуда получать данные OSM

Получить данные можно двумя способами:

- **Через Overpass** — запросить дороги небольшого района. Это удобно для знакомства с OSM и первых примеров.
- **Скачать готовую выгрузку PBF**, например с Geofabrik. Это удобно для экспериментов: один сохранённый файл используется во всех запусках.

Файлы с названием `latest` регулярно обновляются. Если скачать такой файл повторно, дороги и их свойства могут уже измениться. Поэтому нужно сохранить исходный файл и его **контрольную сумму** — цифровой отпечаток, позволяющий проверить, что используется та же версия данных.

**Загружать нужно территорию шире тестовой зоны.** Например, если полигон перекрывает улицу, маршрут может обходить её через соседний район. Если дороги соседнего района не загружены, алгоритм не найдёт объезд, хотя в действительности он существует.

Источники: [Geofabrik](https://download.geofabrik.de/), [Overpass QL](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL).

## 10. Качество данных и выводы ошибок

Для данной курсовой работы следует проверить качество **выбранного набора**, а не исходить из предположения об одинаковой полноте всей мировой базы.

| Возможная проблема | Как влияет на исследование | Что зафиксировать |
|---|---|---|
| Нет координат ссылочного узла | Невозможно собрать линию | Количество и IDs ошибок |
| Пропущена дорога | Искусственный разрыв связности | Локальная проверка на карте |
| Не распознано ограничение | Неправильная доступность | Список неподдерживаемых правил |
| Не задана скорость | Нужна оценка профиля | Правило и число подстановок |
| Слишком мала выгрузка | Теряются объезды | Граница загрузки и её запас |
| Утрачена часть геометрии | Ошибки пересечения с полигонами | Проверка длин и линий |
| Объединены разные уровни | Появился несуществующий поворот | Топология, `bridge/tunnel/layer` |

Если часть семантики не реализована, это ограничивает интерпретацию маршрутов, но не обязательно мешает сравнивать геометрические методы. Для этого у методов должны быть одинаковые входные ограничения, а выводы должны относиться именно к ним.

## 11. Минимальные данные для эксперимента

Ниже предлагается схема исследовательского набора. Названия полей — соглашение стенда, а не стандарт OSM.

### 11.1. Источник и вершины

| Поле | Зачем хранить |
|---|---|
| `snapshot_id`, `source_sha256` | Идентичность исходных данных |
| `graph_version`, `profile_id` | Правила построения графа |
| `node_id`, `osm_node_id` | Внутренняя и исходная идентификация |
| `lon`, `lat` | Исходные координаты: lon - долгота, lat - ширина |
| `geom` | Геометрия в указанной CRS |
| `tags` | Значимые исходные теги узла |

Синтетические вершины после разбиения ребра не обязаны иметь `osm_node_id`. Их происхождение нужно хранить отдельно: например, исходное ребро и расстояние вдоль него.

### 11.2. Рёбра

| Поле / группа | Обязательность для первого стенда | Назначение |
|---|---|---|
| `edge_id`, `u`, `v`, `key` | Обязательно | Направленное ребро |
| `osm_way_id` / ordered source segments | Обязательно | Прослеживаемость |
| `geometry`, `crs` | Обязательно | Полная линия для пересечений |
| `length_m` | Обязательно | База длины и доли воздействия |
| `highway` | Обязательно | Класс дороги |
| `oneway`, access-теги | Обязательно сохранить и интерпретировать по профилю | Допуск направлений |
| `bridge`, `tunnel`, `layer` | Обязательно сохранить | Разбор уровней |
| `maxspeed_raw`, `speed_kph`, `speed_source` | Для модели времени | Исходная и принятая скорость |
| `base_cost`, `scenario_cost` | Обязательно | Независимое сравнение сценариев |
| `surface`, `service`, `name`, `ref` | Желательно | Анализ и объяснение результатов |
| Условные и транспортные ограничения | Сохранить при наличии | Поддержать или явно исключить из модели |

### 11.3. Ограничения и происхождение

Поворотные отношения и их обработка должны храниться независимо от таблицы линий. Для каждого преобразования полезно иметь запись: версия импортёра, правило, число затронутых объектов и число ошибок.

После обновления OSM прежний `way_id` не гарантирует неизменность геометрии и сегментации. Поэтому идентификаторы должны использоваться вместе со снимком и версией графа. Связывать сохранённые полигональные результаты с новым графом без повторной проверки нельзя.

## 12. Что OSM даёт, а что проект должен определить сам

OSM предоставляет данные о дорогах, а в курсовой определяются правила построения графа и изменения стоимости его рёбер под воздействием пользовательских полигонов.

## 13. Лицензия и указание источника данных

Данные OSM распространяются по ODbL. При использовании необходимо указывать OpenStreetMap и участников; для распространяемых производных баз могут возникать дополнительные условия лицензии. Это не означает, что любая программа, читающая OSM, автоматически должна получить ту же лицензию.

На картах и в описании набора следует дать атрибуцию, например `© OpenStreetMap contributors`, со ссылкой на страницу авторских прав. Перед публичным распространением набора нужно проверить условия для конкретного результата.

Источник: [OpenStreetMap — Copyright and License](https://www.openstreetmap.org/copyright).
