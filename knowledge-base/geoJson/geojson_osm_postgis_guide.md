# GeoJSON, геометрии и OpenStreetMap: форматирование, хранение и обработка полигонов

**Практическое руководство для работы с `Polygon`, `MultiPolygon` и `LineString` в связке с OpenStreetMap**  
**Дата подготовки:** 7 ноября 2026 г.  
**Основной нормативный источник:** IETF [RFC 7946 — The GeoJSON Format](https://www.rfc-editor.org/rfc/rfc7946.html). Текст RFC также был приложен к задаче (`rfc7946.txt`).

## 0. Краткие выводы и рекомендуемая архитектура

Если задача — хранить свои полигоны, получать геометрию объектов OpenStreetMap, выполнять пространственные запросы и показывать результат поверх карты, то удобно разделить систему на четыре слоя:

1. **Источник данных OSM.** Для массовой загрузки используйте OSM PBF (или XML для небольших выгрузок), а не GeoJSON как первичное представление исходной базы OSM. В OSM объекты представлены узлами, линиями-списками узлов и отношениями между объектами.
2. **Хранилище и серверная обработка.** Для многопользовательского или достаточно крупного проекта — PostgreSQL + PostGIS. В PostGIS можно хранить геометрию в типизированном столбце `geometry`, атрибуты — в обычных SQL-столбцах и/или `jsonb`, а для ускорения пространственных запросов создать индекс GiST.
3. **Подготовка данных.** Для Python-процессинга подойдут GeoPandas и Shapely; для импорта, экспорта, перепроецирования и пакетной конвертации — GDAL/OGR (`ogr2ogr`). Для первоначальной загрузки OSM в PostgreSQL — `osm2pgsql`, предпочтительно с Flex Output.
4. **Карта.** На клиент отдавайте GeoJSON для небольших и средних наборов данных. Для очень больших наборов, частых обновлений или масштабирования карты рассмотрите векторные тайлы (например, Mapbox Vector Tiles), а не один гигантский GeoJSON-файл. Отображать GeoJSON можно, например, через Leaflet или MapLibre GL JS.

**Рекомендуемый стек по умолчанию:** `OSM PBF → osm2pgsql (Flex) → PostgreSQL/PostGIS → проверки и пространственные операции → GeoJSON RFC 7946 → Leaflet/MapLibre поверх базовой карты`. Для небольшого автономного проекта без отдельного сервера разумная альтернатива — GeoPackage или SpatiaLite.

Важнейшее различие: **GeoJSON — формат представления/обмена геоданными; PostGIS и SpatiaLite — пространственные расширения баз данных; Shapely и GeoPandas — библиотеки обработки; Leaflet и MapLibre — библиотеки отображения.** Это не взаимозаменяемые аналоги одного уровня.

Источники: [RFC 7946](https://www.rfc-editor.org/rfc/rfc7946.html), [OSM: Elements](https://wiki.openstreetmap.org/wiki/Elements), [osm2pgsql Manual](https://osm2pgsql.org/doc/manual.html), [GDAL: OSM driver](https://gdal.org/en/stable/drivers/vector/osm.html), [MapLibre: GeoJSON source](https://maplibre.org/maplibre-gl-js/docs/API/classes/GeoJSONSource/).

## 1. Что такое GeoJSON

### 1.1. Определение и назначение

**GeoJSON** — текстовый формат обмена географическими данными, основанный на JSON. Он описывает геометрию объектов, их атрибуты и, при необходимости, пространственные границы. Спецификация стандартизована IETF в документе [RFC 7946](https://www.rfc-editor.org/rfc/rfc7946.html), опубликованном в августе 2016 года.

GeoJSON удобен для:

- передачи геометрий между сервером, браузером, ГИС и API;
- хранения небольших и средних наборов пространственных объектов в файлах `.geojson` или `.json`;
- отображения точек, линий и полигонов на веб-карте;
- обмена результатами обработки между PostGIS, QGIS, GDAL, Python-библиотеками и веб-клиентом;
- хранения атрибутов объектов вместе с их геометрией.

GeoJSON — **не** специализированная база данных: сам формат не обеспечивает пространственные индексы, конкурентный доступ, транзакции, быстрый поиск пересечений или топологическое редактирование. Это обеспечивает внешняя база данных или библиотека.

Источники: [RFC 7946, разделы 1–3](https://www.rfc-editor.org/rfc/rfc7946.html#section-1), [IANA Media Types: application/geo+json](https://www.iana.org/assignments/media-types/application/geo+json), [GDAL GeoJSON driver](https://gdal.org/en/stable/drivers/vector/geojson.html).

### 1.2. Три уровня объектов: Geometry, Feature, FeatureCollection

Спецификация описывает не только виды геометрии, но и способы упаковки геометрий в объекты.

- **Geometry** — собственно геометрия: например, один `Polygon` или `LineString`.
- **Feature** — один пространственный объект: геометрия плюс атрибуты (`properties`), а при необходимости и идентификатор (`id`). Например, участок леса с названием, категорией и идентификатором исходного объекта OSM.
- **FeatureCollection** — упорядоченный массив объектов `Feature`. Это наиболее удобная оболочка для передачи набора объектов на карту.

Пример `Feature`:

```json
{
  "type": "Feature",
  "id": "forest-001",
  "geometry": {
    "type": "Polygon",
    "coordinates": [
      [
        [13.40, 52.50],
        [13.41, 52.50],
        [13.41, 52.51],
        [13.40, 52.51],
        [13.40, 52.50]
      ]
    ]
  },
  "properties": {
    "name": "Example forest",
    "source": "survey",
    "landuse": "forest"
  }
}
```

Пример `FeatureCollection`:

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "id": 1,
      "geometry": {
        "type": "LineString",
        "coordinates": [[13.40, 52.50], [13.41, 52.51]]
      },
      "properties": {"name": "Example path", "kind": "footway"}
    }
  ]
}
```

Поле `properties` может содержать обычные JSON-значения: строки, числа, логические значения, массивы, вложенные объекты или `null`. Геометрия и атрибуты разделены намеренно: геометрия отвечает за положение и форму, свойства — за смысл объекта.

Для собственного набора данных полезно сохранять исходный идентификатор и происхождение объекта в свойствах, например `osm_type`, `osm_id`, `osm_version`, `source` и `updated_at`. Это облегчает сопоставление геометрии с исходным объектом и повторную загрузку. При этом RFC разрешает `Feature.id` быть строкой или числом; если идентификатор находится внутри `properties`, это уже соглашение приложения, а не требование RFC.

Источники: [RFC 7946, Feature Object](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.2), [RFC 7946, FeatureCollection Object](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.3), [GDAL: Feature mapping](https://gdal.org/en/stable/drivers/vector/geojson.html#feature).

### 1.3. Система координат и порядок координат — критически важно

Для GeoJSON по RFC 7946 используется географическая система координат на датуме **WGS 84**, эквивалентная `OGC:CRS84`, с угловыми единицами в десятичных градусах. Координаты записываются строго в порядке:

```text
[longitude, latitude]
[долгота, широта]
```

Не наоборот. Например, точка в районе Берлина может выглядеть примерно так:

```json
{"type": "Point", "coordinates": [13.4050, 52.5200]}
```

Третья координата допускается как высота в метрах относительно эллипсоида WGS 84:

```json
{"type": "Point", "coordinates": [13.4050, 52.5200, 38.0]}
```

RFC рекомендует не расширять позицию более чем тремя числами: смысл четвёртой и последующих координат не определён единообразно. Не следует помещать в четвёртую координату время или M-значение, рассчитывая на то, что все программы поймут его одинаково.

**В RFC 7946 удалён механизм задания произвольной CRS через поле `crs`.** Поэтому данные в проекционной системе, например Web Mercator `EPSG:3857`, нельзя просто записать в GeoJSON и считать стандартным RFC 7946. Перед экспортом нужно преобразовать координаты в WGS 84 / CRS84. В PostGIS для этого используется `ST_Transform`, а не `ST_SetSRID`.

Практическая оговорка об EPSG:4326: в GeoJSON порядок координат — именно долгота/широта, как в CRS84. В некоторых API и библиотеках формальная осевая последовательность EPSG:4326 может трактоваться иначе. Проверяйте контракт конкретной библиотеки, но при создании RFC 7946 GeoJSON придерживайтесь `[lon, lat]`.

Источники: [RFC 7946, Position](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.1), [RFC 7946, Coordinate Reference System](https://www.rfc-editor.org/rfc/rfc7946.html#section-4), [PostGIS: ST_Transform](https://postgis.net/docs/ST_Transform.html), [GDAL GeoJSON RFC7946 write support](https://gdal.org/en/stable/drivers/vector/geojson.html#rfc-7946-write-support).

### 1.4. Все типы GeoJSON

RFC 7946 устанавливает семь типов геометрии и два типа объектов-обёрток. Названия регистрозависимы.

| Тип                  | Размерность | Смысл                                                        | Пример применения                                         |
| -------------------- | ----------: | ------------------------------------------------------------ | --------------------------------------------------------- |
| `Point`              |          0D | Одна точка                                                   | Остановка, вход, объект инфраструктуры                    |
| `MultiPoint`         |          0D | Набор точек                                                  | Несколько точек наблюдения, группа объектов               |
| `LineString`         |          1D | Одна связная последовательность отрезков                     | Дорога, тропа, река, граница маршрута                     |
| `MultiLineString`    |          1D | Несколько линий                                              | Разорванный маршрут, несколько участков линейного объекта |
| `Polygon`            |          2D | Одна поверхность с внешней границей и возможными отверстиями | Здание, участок, парк, озеро                              |
| `MultiPolygon`       |          2D | Набор полигонов                                              | Архипелаг, несколько несмежных частей территории          |
| `GeometryCollection` |   смешанная | Набор геометрий разных типов                                 | Композиция точки, линии и полигона                        |

Кроме геометрий, в спецификации есть `Feature` и `FeatureCollection`. Они **не являются типами геометрии**, а задают структуру данных вокруг геометрии.

`LinearRing` (линейное кольцо) часто встречается в описаниях полигонов и в API геометрических библиотек, но самостоятельным GeoJSON geometry type не является. Внутри GeoJSON кольцо записывается как массив координат в `Polygon`.

Источники: [RFC 7946, разделы 1.4 и 3.1](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1), [OGC Simple Feature Access](https://www.ogc.org/standards/sfa/).

### 1.5. Общие ограничения и тонкости формата

1. **Прямолинейная интерполяция.** По RFC отрезок между соседними позициями — прямая линия в координатном пространстве, а не автоматически геодезическая дуга по поверхности Земли. На больших расстояниях и при пересечении значимых участков земной поверхности это может иметь заметное значение.
2. **Антимеридиан.** Объекты, пересекающие линию ±180° долготы, рекомендуется разрезать на части, чтобы отдельные представления не пересекали антимеридиан. Для линии примером будет `MultiLineString`, для области — `MultiPolygon`.
3. **Точность записи.** Количество знаков после запятой не является гарантией фактической точности измерения. RFC отмечает, что шесть знаков после запятой в градусных координатах соответствуют примерно 10 см и обычно достаточны для многих задач; увеличение точности может заметно увеличить размер GeoJSON.
4. **`bbox`.** Опциональное поле. Для двумерных координат порядок значений — `[west, south, east, north]`. Это не координаты произвольной вершины полигона. Для bbox, пересекающего антимеридиан, восточная долгота может быть меньше западной.
5. **Пустая геометрия.** RFC допускает, что обработчик интерпретирует пустой массив `coordinates` как null-объект. Лучше явно определить политику приложения для пустых геометрий.
6. **Расширения.** Можно добавлять сторонние поля, но они не меняют семантику стандартных полей. Совместимость дополнительных полей зависит от обработчиков.

Источники: [RFC 7946, Position и прямые линии](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.1), [Antimeridian Cutting](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.9), [Uncertainty and Precision](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.10), [Bounding Box](https://www.rfc-editor.org/rfc/rfc7946.html#section-5), [Extending GeoJSON](https://www.rfc-editor.org/rfc/rfc7946.html#section-6).

## 2. Тип `Polygon`

### 2.1. Что представляет собой Polygon

`Polygon` — двумерная поверхность, ограниченная одним внешним линейным кольцом; внутри могут находиться одно или несколько отверстий. Типичное применение — границы земельного участка, озера, леса, административной территории, здания или зоны действия правила.

В отличие от `LineString`, полигон описывает не только границу, но и **заполненную область внутри неё**. Поэтому операции над полигоном могут включать вычисление площади, принадлежность точки, пересечение с другими областями, объединение, вычитание и построение буфера.

### 2.2. Структура координат

Структура `coordinates` у `Polygon` — массив линейных колец:

```text
coordinates = [ exterior_ring, hole_1, hole_2, ... ]
```

- первое кольцо всегда внешнее — оно задаёт границу поверхности;
- последующие кольца — внутренние, они задают отверстия;
- каждое кольцо — замкнутая последовательность координат.

Пример полигона без отверстий:

```json
{
  "type": "Polygon",
  "coordinates": [
    [
      [13.4000, 52.5000],
      [13.4100, 52.5000],
      [13.4100, 52.5100],
      [13.4000, 52.5100],
      [13.4000, 52.5000]
    ]
  ]
}
```

Пример полигона с отверстием (внутреннее кольцо исключает область из поверхности):

```json
{
  "type": "Polygon",
  "coordinates": [
    [
      [13.4000, 52.5000],
      [13.4100, 52.5000],
      [13.4100, 52.5100],
      [13.4000, 52.5100],
      [13.4000, 52.5000]
    ],
    [
      [13.4020, 52.5020],
      [13.4020, 52.5080],
      [13.4080, 52.5080],
      [13.4080, 52.5020],
      [13.4020, 52.5020]
    ]
  ]
}
```

Обратите внимание на количество уровней массивов: у `Polygon` внешний массив содержит кольца, а каждое кольцо содержит позиции `[lon, lat]`.

Источник: [RFC 7946, Polygon](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.6) и [примеры полигонов в Appendix A.3](https://www.rfc-editor.org/rfc/rfc7946.html#appendix-A.3).

### 2.3. Требования к Linear Ring

RFC 7946 определяет линейное кольцо (`LinearRing`) как замкнутый `LineString`, состоящий как минимум из четырёх позиций:

- первая и последняя позиции должны иметь одинаковые значения;
- кольцо должно быть замкнуто явно — простого геометрического совпадения концов без повторной последней координаты недостаточно для корректного представления по RFC;
- внешнее кольцо должно идти против часовой стрелки (counterclockwise);
- внутренние кольца должны идти по часовой стрелке (clockwise).

Это правило ориентации известно как **правило правой руки (right-hand rule)**. RFC рекомендует обработчикам не отвергать старые полигоны только из-за неправильного порядка обхода колец — это сделано для обратной совместимости. Но при создании новых данных правильно ориентировать кольца следует.

Нюанс: соблюдение требований к замыканию и направлению обхода ещё не исчерпывает все проверки валидности полигона. Например, самопересекающийся контур может быть формально записан как массив координат, но оставаться топологически некорректной геометрией по правилам OGC Simple Features. Для проверки применяют `ST_IsValid` в PostGIS или `is_valid` в Shapely.

Источники: [RFC 7946, Linear Ring](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.6), [OGC Simple Feature Access](https://www.ogc.org/standards/sfa/), [PostGIS: ST_IsValid](https://postgis.net/docs/ST_IsValid.html).

### 2.4. Что может пойти не так с Polygon

Типичные проблемы при сборке и редактировании:

- **Незамкнутое кольцо:** первая и последняя координаты отличаются.
- **Недостаточно координат:** меньше четырёх позиций в кольце.
- **Самопересечение:** например, контур в форме «банта» (bow-tie).
- **Неверная структура вложенности:** перепутаны уровни массивов или внутреннее кольцо записано вместо внешнего.
- **Отверстие за пределами внешнего кольца** или пересечение отверстий между собой.
- **Ошибочная CRS или порядок осей:** долгота и широта перепутаны, либо метры Web Mercator приняты за градусы.
- **Чрезмерная детализация:** очень много вершин ухудшает передачу, хранение и скорость отображения.

`ST_MakeValid` в PostGIS пытается исправить невалидную геометрию, но результатом может оказаться не один `Polygon`, а `MultiPolygon` или геометрия другого типа, если исходный объект вырождается или распадается. После исправления обязательно проверяйте тип и смысл результата, а не только факт успешного выполнения функции.

Источники: [PostGIS: ST_IsValid](https://postgis.net/docs/ST_IsValid.html), [PostGIS: ST_MakeValid](https://postgis.net/docs/ST_MakeValid.html), [Shapely User Manual](https://shapely.readthedocs.io/en/stable/manual.html).

### 2.5. Какие операции обычно нужны для полигонов

| Операция | Смысл | Типичный пример |
|---|---|---|
| `ST_Area` | Площадь | Площадь парка или участка |
| `ST_Perimeter` | Периметр | Длина границы территории |
| `ST_Contains` / `ST_Covers` | Проверка включения | Входит ли точка или участок в зону |
| `ST_Intersects` | Пересечение | Пересекает ли дорога территорию |
| `ST_Intersection` | Геометрическое пересечение | Вырезать часть полигона в пределах района |
| `ST_Union` | Объединение | Слить соседние участки в общую область |
| `ST_Difference` | Разность | Исключить водоём или заповедную зону |
| `ST_Buffer` | Буфер вокруг геометрии | Создать охранную/защитную зону |
| `ST_SimplifyPreserveTopology` | Упрощение с сохранением топологии отдельной геометрии | Уменьшить число вершин перед отправкой на карту |
| `ST_IsValid` / `ST_MakeValid` | Проверка и попытка исправления валидности | Очистка импортированных данных |

Важное отличие `ST_Contains` от `ST_Covers`: точка, лежащая ровно на границе полигона, не считается находящейся в его внутренности для `ST_Contains`; если граница тоже должна считаться включённой, проверьте применимость `ST_Covers`.

Источники: [PostGIS Reference: Spatial Relationships](https://postgis.net/docs/reference.html), [PostGIS: ST_IsValid](https://postgis.net/docs/ST_IsValid.html), [PostGIS: ST_MakeValid](https://postgis.net/docs/ST_MakeValid.html).

## 3. Тип `MultiPolygon`

### 3.1. Что представляет собой MultiPolygon

`MultiPolygon` — одна геометрия, объединяющая несколько полигонов. Он полезен, когда один логический объект состоит из нескольких раздельных частей: архипелаг, территория муниципалитета с анклавами, группа островов, несколько несмежных участков одного объекта или область, разрезанная антимеридианом.

`MultiPolygon` не то же самое, что массив независимых `Feature`. В первом случае это **одна геометрия одного объекта**; во втором — несколько объектов с отдельными идентификаторами и свойствами.

Примеры:

- один муниципалитет с основной территорией и отдельным островом — часто один `MultiPolygon`;
- три независимых земельных участка разных владельцев — вероятнее всего три `Feature` с типом `Polygon`, даже если их можно технически объединить в `MultiPolygon`;
- территория с одним или несколькими отверстиями и ещё одной изолированной частью — `MultiPolygon`, в одном из компонентов которого есть внутренние кольца.

Источник: [RFC 7946, MultiPolygon](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.7) и [OGC SFA](https://www.ogc.org/standards/sfa/).

### 3.2. Структура coordinates

`coordinates` у `MultiPolygon` — массив координат полигонов. То есть каждый элемент внешнего массива имеет ту же структуру, что и `coordinates` у одного `Polygon`:

```text
coordinates = [
  polygon_1 = [ exterior_ring, hole_1, ... ],
  polygon_2 = [ exterior_ring, hole_1, ... ],
  ...
]
```

Пример двух раздельных полигонов:

```json
{
  "type": "MultiPolygon",
  "coordinates": [
    [
      [
        [13.4000, 52.5000],
        [13.4100, 52.5000],
        [13.4100, 52.5100],
        [13.4000, 52.5100],
        [13.4000, 52.5000]
      ]
    ],
    [
      [
        [13.4300, 52.5000],
        [13.4400, 52.5000],
        [13.4400, 52.5100],
        [13.4300, 52.5100],
        [13.4300, 52.5000]
      ]
    ]
  ]
}
```

Пример одного `MultiPolygon`, у которого второй компонент имеет отверстие:

```json
{
  "type": "MultiPolygon",
  "coordinates": [
    [
      [
        [13.40, 52.50], [13.41, 52.50],
        [13.41, 52.51], [13.40, 52.51], [13.40, 52.50]
      ]
    ],
    [
      [
        [13.43, 52.50], [13.44, 52.50],
        [13.44, 52.51], [13.43, 52.51], [13.43, 52.50]
      ],
      [
        [13.432, 52.502], [13.432, 52.508],
        [13.438, 52.508], [13.438, 52.502], [13.432, 52.502]
      ]
    ]
  ]
}
```

Уровень вложенности здесь особенно важен: `MultiPolygon → Polygon → LinearRing → Position`.

Источник: [RFC 7946, MultiPolygon и Appendix A.6](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.7).

### 3.3. Отличие Polygon от MultiPolygon

| Критерий | `Polygon` | `MultiPolygon` |
|---|---|---|
| Количество внешних контуров | Один | Несколько — по одному на компонент-полигон |
| Отверстия | Да, внутренние кольца | Да, у каждого компонента могут быть свои внутренние кольца |
| Применение | Одна связная область | Один объект с несколькими частями |
| Уровень вложенности координат | Кольца → позиции | Полигоны → кольца → позиции |

Не стоит автоматически преобразовывать все объекты в `MultiPolygon` только потому, что это упрощает схему БД. Это допустимая стратегия хранения, если она согласована с приложением (например, колонка `geometry(MultiPolygon, 4326)`), но нужно помнить, что при экспорте и обработке тип может отличаться от исходного. Для единого типа хранения можно нормализовать `Polygon` через `ST_Multi`, а при выдаче клиенту, которому важна исходная форма, вернуть подходящий тип.

### 3.4. MultiPolygon и валидность

Для `MultiPolygon` недостаточно, чтобы каждый отдельный контур был замкнут. Важны также взаимные отношения частей: области внутренних частей разных компонентов не должны некорректно перекрываться. Правила проверки определяются моделью Simple Features и реализацией геометрического движка.

После `ST_Union`, `ST_MakeValid`, `ST_Intersection` и других операций результат может менять тип: например, один `Polygon` может превратиться в `MultiPolygon`, а пересечение — дать линию или точку, если области лишь соприкасаются. Поэтому приложение должно быть готово к результатам разных размерностей или явно извлекать ожидаемые компоненты (`ST_CollectionExtract`).

Источники: [OGC Simple Feature Access](https://www.ogc.org/standards/sfa/), [PostGIS: ST_MakeValid](https://postgis.net/docs/ST_MakeValid.html), [PostGIS Reference](https://postgis.net/docs/reference.html).

## 4. Тип `LineString`

### 4.1. Что представляет собой LineString

`LineString` — упорядоченная последовательность двух или более позиций, соединённых отрезками. Это одномерная геометрия: у неё есть длина, но нет площади.

Типичные применения в OSM-контексте:

- дорожный сегмент;
- пешеходная или велосипедная тропа;
- русло реки или канал;
- маршрут или часть маршрута;
- линейная граница, если задача моделируется именно как линия, а не как заполненная поверхность.

Порядок координат имеет значение: он задаёт направление линии. Разворот `LineString` не меняет его геометрическое множество, но может менять смысл направления движения, порядок обхода маршрута или логику «слева/справа».

### 4.2. Структура и пример

В `coordinates` находится массив позиций. Согласно RFC, их должно быть как минимум две:

```json
{
  "type": "LineString",
  "coordinates": [
    [13.4000, 52.5000],
    [13.4050, 52.5020],
    [13.4100, 52.5050]
  ]
}
```

Каждая соседняя пара позиций формирует отрезок. Повторяющиеся координаты технически встречаются, но обычно не несут пользы и могут ухудшать производительность или создавать проблемы дальнейшей обработки.

Источник: [RFC 7946, LineString](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.4) и [Shapely User Manual: LineStrings](https://shapely.readthedocs.io/en/stable/manual.html#linestrings).

### 4.3. LineString не обязательно является простой линией

Линия может самопересекаться. Поэтому нужно различать:

- **валидность геометрии** — соответствует ли объект правилам для его типа;
- **простоту линии (`is_simple`)** — нет ли у неё самопересечений и других особенностей, нарушающих простоту.

Самопересекающийся маршрут может быть допустимым сценарием. Например, маршрут может пересекать себя на развязке или в спортивной трассе. Поэтому нельзя объявлять любую самопересекающуюся линию ошибочной без учёта предметной задачи.

### 4.4. LineString и расстояние на Земле

Есть важная геодезическая тонкость. RFC определяет сегмент GeoJSON как прямой отрезок в координатном пространстве, а не обязательно как геодезическую линию на эллипсоиде Земли. Если линия короткая и локальная, разница для визуализации обычно несущественна. Для длинных маршрутов, измерения километров и точного буферизования нужно выбрать подходящий способ вычисления:

- перепроецировать геометрию в локальную метрическую проекцию и считать длину в метрах;
- либо использовать тип `geography` в PostGIS для поддерживаемых геодезических операций;
- не рассчитывать длину в метрах напрямую по `geometry` с SRID 4326: единицы такой геометрии — градусы.

Для линии особенно полезны `ST_Length`, `ST_DWithin`, `ST_Intersects`, `ST_LineLocatePoint`, `ST_LineInterpolatePoint`, `ST_Split`, `ST_SimplifyPreserveTopology` и пространственные индексы.

Источники: [RFC 7946, Position / straight Cartesian line](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.1), [PostGIS FAQ: geometry or geography?](https://postgis.net/documentation/faq/geometry-or-geography/), [Shapely Manual](https://shapely.readthedocs.io/en/stable/manual.html).

## 5. Как GeoJSON соотносится с OpenStreetMap

### 5.1. OSM — не GeoJSON-база

OpenStreetMap (OSM) хранит данные в собственной концептуальной модели. В ней три базовых элемента:

1. **Node** — точка с координатами.
2. **Way** — упорядоченный список узлов. Может представлять линию или границу площади.
3. **Relation** — упорядоченная группа узлов, линий и/или других отношений с ролями участников; используется для описания более сложных объектов и связей.

У каждого элемента могут быть теги `key=value`, задающие смысл: например, `highway=primary`, `building=yes`, `landuse=forest`, `natural=water`.

Следовательно, OSM Way не равен автоматически GeoJSON `LineString`, а OSM Relation не равна автоматически GeoJSON `MultiPolygon`. Между моделями выполняется преобразование и интерпретация тегов и ролей.

Источники: [OSM Wiki: Elements](https://wiki.openstreetmap.org/wiki/Elements), [OSM XML format](https://wiki.openstreetmap.org/wiki/OSM_XML).

### 5.2. Закрытый Way — не всегда полигон

Если первый и последний узлы Way совпадают, Way является замкнутым. Но из этого **не следует**, что он обязательно обозначает заполненную площадь.

Например:

- замкнутый `landuse=forest` обычно трактуется как площадь;
- замкнутый `highway=*` может обозначать кольцевую дорогу или круговое движение;
- в неоднозначных случаях используются теги `area=yes` или `area=no`.

Таким образом, при экспорте OSM в GeoJSON недостаточно проверить, что линия замкнута. Нужно учитывать теги и правила предметной области. Программа, которая превратит любой замкнутый Way в `Polygon`, будет выдавать неверную геометрию для некоторых объектов.

Источники: [OSM Wiki: Area](https://wiki.openstreetmap.org/wiki/Area-implying_tags), [OSM Wiki: Way](https://wiki.openstreetmap.org/wiki/Way), [OSM Wiki: `area=*`](https://wiki.openstreetmap.org/wiki/Key:area).

### 5.3. OSM multipolygon relation и GeoJSON MultiPolygon — разные уровни модели

В OSM сложные площади моделируются отношением с тегом `type=multipolygon`. Его участниками выступают Ways с ролями:

- `outer` — части внешней границы;
- `inner` — части границ отверстий.

Внешняя и внутренняя границы могут состоять из нескольких отдельных Ways. При обработке их нужно соединить в замкнутые кольца, правильно определить, какие кольца внешние, а какие внутренние, и собрать результирующие полигоны. Один объект OSM может представляться как `Polygon` или `MultiPolygon`, в зависимости от количества несвязанных частей.

Именно поэтому OSM multipolygon relation — это структура исходных данных и топологическая связь элементов, а GeoJSON MultiPolygon — уже собранная геометрия. При экспорте теряется часть исходной структуры: какие фрагменты границы были отдельными Ways, какие имели свои идентификаторы и как именно relation ссылалась на участников. Если эта информация нужна для редактирования или аудита, сохраняйте идентификаторы и исходные связи отдельно.

Источники: [OSM Wiki: Multipolygon relation](https://wiki.openstreetmap.org/wiki/Relation:multipolygon), [OSM Wiki: Relation](https://wiki.openstreetmap.org/wiki/Relation), [OSM Wiki: Elements](https://wiki.openstreetmap.org/wiki/Elements).

### 5.4. OSM routes и LineString / MultiLineString

Линейные OSM-объекты часто переводятся в `LineString`; отношение маршрута может быть преобразовано в `MultiLineString` или другой набор линий. Но route relation может содержать порядок и роли участников (`forward`, `backward`, `platform`, `stop` и др.), а также метаданные. Простое объединение всех сегментов в одну линию может потерять порядок, направление, остановки или логическую структуру маршрута.

Если задача — только визуализация контура маршрута, GeoJSON часто достаточен. Если строится маршрутизация, анализ связности дорог или редактирование OSM, сохраните исходные Ways и Relations и рассматривайте маршрутную/графовую модель отдельно.

Источники: [OSM Wiki: Elements](https://wiki.openstreetmap.org/wiki/Elements), [OSM Wiki: Relation](https://wiki.openstreetmap.org/wiki/Relation), [OSM file formats](https://wiki.openstreetmap.org/wiki/OSM_file_formats).

### 5.5. Получение OSM-данных и конвертация

Основные форматы данных OSM:

- **PBF** — компактный двоичный формат, обычно предпочтительный для обработки выгрузок;
- **OSM XML (`.osm`)** — текстовый XML, полезный для чтения и небольших примеров, но большие выгрузки занимают много места;
- **Overpass JSON** — ответ Overpass API, но это не GeoJSON, несмотря на сходство названий.

Overpass API позволяет выполнять запросы к OSM по тегам, типам объектов и областям. Результат `out:json` содержит OSM-элементы в формате API; сам по себе он не является `FeatureCollection` RFC 7946. Для перехода к GeoJSON нужно собрать геометрию по узлам/участникам relation — например, с помощью конвертера или GIS-инструмента.

GDAL/OGR умеет читать OSM XML и PBF и реконструировать геометрии из Nodes, Ways и Relations. В документации GDAL отдельно отмечено, что для больших файлов такой драйвер может работать медленно; для импорта крупных наборов данных рекомендуется инструмент `osm2pgsql`.

`osm2pgsql` загружает OSM-данные в PostgreSQL и формирует геометрические таблицы. Для новых проектов документация рекомендует Flex Output: с помощью Lua-стиля задаётся, какие объекты попадут в какие таблицы и какие атрибуты/преобразования нужны. Старый `pgsql` Output отмечен как устаревающий.

Источники: [OSM file formats](https://wiki.openstreetmap.org/wiki/OSM_file_formats), [PBF format](https://wiki.openstreetmap.org/wiki/PBF), [Overpass QL](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL), [GDAL OSM driver](https://gdal.org/en/stable/drivers/vector/osm.html), [osm2pgsql Manual](https://osm2pgsql.org/doc/manual.html).

### 5.6. Что сохранять при импорте OSM

Для дальнейшей работы рекомендую хранить не только собранную геометрию, но и метаданные источника:

| Поле | Пример | Зачем |
|---|---|---|
| `osm_type` | `way`, `relation`, `node` | Тип исходного элемента |
| `osm_id` | `123456789` | Идентификатор OSM |
| `osm_version` | `7` | Версия элемента, если доступна в потоке импорта |
| `tags` | JSON-объект | Исходные теги OSM |
| `geom` | `MultiPolygon` | Геометрия для GIS-запросов |
| `source_timestamp` | дата/время | Возраст данных |
| `imported_at` | дата/время | Когда данные загрузили в вашу систему |

Набор OSM-тегов неоднороден: у разных объектов разные ключи и значения. В Postgres удобно сохранять исходные теги в `jsonb`, а часто используемые поля (например, тип объекта, категория, имя, класс дороги) при необходимости выносить в отдельные индексируемые SQL-колонки.

### 5.7. Лицензия OSM

Данные OpenStreetMap распространяются по лицензии **Open Data Commons Open Database License (ODbL)**. При использовании данных необходимо указывать OpenStreetMap и участников, соблюдать правила атрибуции и учитывать условия лицензии при распространении производных баз данных. Для публичной карты обычно отображают атрибуцию, например `© OpenStreetMap contributors`, со ссылкой на страницу лицензии. Для конкретного способа распространения данных нужно проверять требования ODbL, а не полагаться только на наличие открытого доступа к данным.

Источник: [OpenStreetMap — Copyright and License](https://www.openstreetmap.org/copyright).

## 6. Хранение геометрий: форматы и базы данных

### 6.1. Не путайте GeoJSON, WKT, WKB и тип `geometry`

| Представление | Что это | Когда удобно | Основной недостаток |
|---|---|---|---|
| GeoJSON | Текстовый JSON с Geometry/Feature/FeatureCollection | API, веб-карты, обмен | Многословен; нет встроенного пространственного индекса |
| WKT | Текстовая запись геометрии, например `POLYGON((...))` | Отладка, SQL-примеры, ручная проверка | Не содержит обычной модели Feature/Properties; текст объёмный |
| WKB | Двоичная запись геометрии | Хранение и обмен между GIS-библиотеками/БД | Неудобна для просмотра человеком; обычный WKB сам по себе не описывает атрибуты Feature |
| EWKT / EWKB | Расширения WKT/WKB с дополнительной информацией, например SRID | Обмен с PostGIS и некоторыми GIS-инструментами | Не являются форматом GeoJSON RFC 7946 |
| PostGIS `geometry` | Пространственный тип в PostgreSQL | Запросы, индексы, анализ, транзакционное хранение | Требует PostgreSQL и расширения PostGIS |
| GeoPackage | Файл SQLite по стандарту OGC | Обмен слоями, автономная работа, мобильные и desktop GIS | Файловая БД, не эквивалент полноценному серверному PostGIS для многопользовательской нагрузки |

GeoJSON следует рассматривать как удобный внешний формат, а не обязательный формат физического хранения в БД. Например, PostGIS хранит геометрию в собственном двоичном представлении и конвертирует её в/из GeoJSON по запросу.

Источники: [RFC 7946](https://www.rfc-editor.org/rfc/rfc7946.html), [PostGIS: Geometry](https://postgis.net/docs/using_postgis_dbmanagement.html), [OGC GeoPackage](https://www.geopackage.org/spec/).

### 6.2. PostGIS — основной кандидат для задачи

**PostGIS** — расширение PostgreSQL, добавляющее пространственные типы данных, индексы и функции. PostgreSQL остаётся реляционной базой данных, а PostGIS расширяет её возможностями для работы с геометрией и географией.

Что он даёт:

- типы `geometry` и `geography`;
- поддержку `Point`, `LineString`, `Polygon`, multipart-типов и `GeometryCollection`;
- ограничения по типу геометрии, SRID и размерности на уровне столбца;
- пространственные индексы, обычно GiST (основанный на R-tree-подобной стратегии индексирования ограничивающих прямоугольников);
- пространственные предикаты: `ST_Intersects`, `ST_Contains`, `ST_Within`, `ST_Covers`, `ST_Touches` и другие;
- измерения и операции: `ST_Area`, `ST_Length`, `ST_Distance`, `ST_Buffer`, `ST_Intersection`, `ST_Union`, `ST_Difference`;
- функции преобразования форматов: `ST_GeomFromGeoJSON`, `ST_AsGeoJSON`, `ST_GeomFromText`, `ST_AsText`, `ST_GeomFromWKB`, `ST_AsBinary`;
- преобразование систем координат через `ST_Transform`;
- проверку и восстановление валидности (`ST_IsValid`, `ST_MakeValid`).

Документация: [PostGIS Manual](https://postgis.net/docs/), [PostGIS Reference](https://postgis.net/docs/reference.html).

#### 6.2.1. `geometry` и `geography`

Это два разных способа интерпретировать координаты:

- `geometry` — геометрия на плоской декартовой плоскости. Единицы результата зависят от CRS: для проекции в метрах — метры, для `EPSG:4326` — градусы. Обычно функции `geometry` быстрее и поддерживают широкий набор операций.
- `geography` — географическая геометрия на поверхности Земли; часть расстояний и площадей рассчитывается с учётом сферической/эллипсоидальной модели. Удобно для глобальных данных и измерений в метрах, но набор поддерживаемых операций меньше, а вычисления обычно дороже.

Практическое правило:

- для точного локального анализа (площадь, длина, буферы, пересечения) обычно выбирайте `geometry` в подходящей локальной проекции с метрическими единицами;
- для глобальных задач, если не хотите самостоятельно подбирать проекцию и нужны поддерживаемые геодезические расстояния/площади, рассмотрите `geography`;
- для выдачи GeoJSON преобразуйте геометрию в WGS 84 / CRS84.

Не рассчитывайте `ST_Area(geom)` или `ST_Length(geom)` в квадратных метрах/метрах, если `geom` хранится как `geometry(...,4326)`: результаты будут в квадратных градусах или градусах, а не в метрических единицах. Используйте подходящую проекцию или `geography` для поддерживаемой операции.

Источники: [PostGIS FAQ: geometry or geography?](https://postgis.net/documentation/faq/geometry-or-geography/), [PostGIS Data Management](https://postgis.net/docs/using_postgis_dbmanagement.html), [ST_Transform](https://postgis.net/docs/ST_Transform.html).

#### 6.2.2. Пример схемы таблицы

Для слоя площадных объектов можно завести таблицу с типом `MultiPolygon` и SRID 4326:

```sql
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE osm_areas (
    id              bigserial PRIMARY KEY,
    osm_type        text NOT NULL,
    osm_id          bigint NOT NULL,
    tags            jsonb NOT NULL DEFAULT '{}'::jsonb,
    source_timestamp timestamptz,
    geom            geometry(MultiPolygon, 4326) NOT NULL,
    UNIQUE (osm_type, osm_id)
);

CREATE INDEX osm_areas_geom_gix
    ON osm_areas
    USING GIST (geom);

CREATE INDEX osm_areas_tags_gin
    ON osm_areas
    USING GIN (tags);
```

Здесь:

- `geometry(MultiPolygon, 4326)` ограничивает колонку типом `MultiPolygon` и SRID 4326;
- `tags jsonb` сохраняет гибкий набор тегов OSM;
- `UNIQUE (osm_type, osm_id)` позволяет различать, например, `way/123` и `relation/123`;
- GiST-индекс ускоряет многие пространственные запросы;
- GIN-индекс может ускорять поиски по JSONB-тегам — подберите индексацию под реальные запросы.

Если слой может содержать и `Polygon`, и `MultiPolygon`, используйте либо общий тип `geometry(Geometry, 4326)` (с меньшей строгостью), либо нормализуйте все полигоны в `MultiPolygon`. Если нужны линии и полигоны, обычно удобнее разделить их на отдельные таблицы/слои с понятными ограничениями.

#### 6.2.3. Импорт GeoJSON в PostGIS

`ST_GeomFromGeoJSON` создаёт объект PostGIS `geometry` из фрагмента GeoJSON типа Geometry. Функция ожидает именно объект геометрии, а не весь `Feature` или `FeatureCollection`. Это частая ошибка при первом импорте.

Пример для JSONB-документа, который содержит `FeatureCollection`:

```sql
-- :doc — параметр с полным GeoJSON FeatureCollection
INSERT INTO osm_areas (osm_type, osm_id, tags, geom)
SELECT
    COALESCE(f->'properties'->>'osm_type', 'unknown'),
    (f->'properties'->>'osm_id')::bigint,
    COALESCE(f->'properties'->'tags', '{}'::jsonb),
    ST_Multi(
        ST_SetSRID(
            ST_GeomFromGeoJSON((f->'geometry')::text),
            4326
        )
    )
FROM jsonb_array_elements((:doc::jsonb)->'features') AS src(f)
WHERE f->'geometry' IS NOT NULL
  AND f->'geometry'->>'type' IN ('Polygon', 'MultiPolygon');
```

В этом примере:

- `jsonb_array_elements` перебирает features;
- `f->'geometry'` извлекает фрагмент Geometry;
- `ST_GeomFromGeoJSON` разбирает геометрию;
- `ST_SetSRID(...,4326)` присваивает SRID, исходя из предположения, что входной документ корректно следует RFC 7946;
- `ST_Multi` нормализует `Polygon` в `MultiPolygon`, а `MultiPolygon` оставляет multipart-геометрией.

В актуальном PostGIS (начиная с 3.0) геометрия из GeoJSON без явного SRID по умолчанию получает SRID 4326, но явное указание SRID может сделать контракт импорта нагляднее. `ST_SetSRID` **не перепроецирует** координаты; он лишь задаёт метку CRS. Если исходные числа на самом деле были в другой системе, сначала нужно установить реальную систему и выполнить `ST_Transform`.

Для реального импорта добавьте обработку отсутствующих/нечисловых `osm_id`, пустых геометрий, неподдерживаемых типов и ошибок валидности. Не вставляйте произвольные JSON-документы без валидации.

Источники: [PostGIS: ST_GeomFromGeoJSON](https://postgis.net/docs/ST_GeomFromGeoJSON.html), [PostGIS: ST_AsGeoJSON](https://postgis.net/docs/ST_AsGeoJSON.html), [PostGIS: ST_Transform](https://postgis.net/docs/ST_Transform.html).

#### 6.2.4. Экспорт в GeoJSON

Чтобы экспортировать геометрию в соответствующий RFC 7946 GeoJSON, преобразуйте её в WGS 84 и только затем сериализуйте:

```sql
SELECT ST_AsGeoJSON(ST_Transform(geom, 4326))
FROM osm_areas;
```

Для возврата объекта `Feature` с атрибутами можно использовать вариант `ST_AsGeoJSON(record, ...)`:

```sql
SELECT ST_AsGeoJSON(t.*, id_column => 'id')
FROM (
    SELECT id, tags, ST_Transform(geom, 4326) AS geom
    FROM osm_areas
) AS t;
```

Если нужен единый `FeatureCollection`, чаще всего результат агрегируют в `jsonb_build_object('type','FeatureCollection', 'features', jsonb_agg(...))` или используют прикладной слой/API. При округлении координат следите, чтобы геометрия после снижения точности оставалась валидной. Документация PostGIS предупреждает, что простое уменьшение количества знаков может испортить валидность; при необходимости сначала используйте точностную сетку/сведение точности с контролем топологии.

Источники: [PostGIS: ST_AsGeoJSON](https://postgis.net/docs/ST_AsGeoJSON.html), [RFC 7946, Coordinate Precision](https://www.rfc-editor.org/rfc/rfc7946.html#section-11.2).

#### 6.2.6. Пространственные индексы и производительность

Пространственный индекс обычно индексирует **ограничивающий прямоугольник** (bounding box) каждой геометрии, а не всю сложную форму целиком. Запрос сначала быстро получает кандидатов по прямоугольникам, а затем выполняется точная геометрическая проверка. Поэтому индекс может вернуть кандидата, который попал в прямоугольник, но не пересекает фактический полигон.

Пример создания индекса:

```sql
CREATE INDEX osm_areas_geom_gix
ON osm_areas
USING GIST (geom);
```

Пример запроса:

```sql
SELECT id, osm_type, osm_id, tags
FROM osm_areas
WHERE ST_Intersects(
    geom,
    ST_SetSRID(ST_MakeEnvelope(13.35, 52.48, 13.45, 52.55), 4326)
);
```

Индекс-aware функции, в том числе `ST_Intersects`, `ST_Contains`, `ST_Within` и `ST_DWithin`, могут автоматически использовать пространственный индекс для первичного отбора. Но это зависит от плана запроса, статистики и формы условия — проверяйте `EXPLAIN (ANALYZE, BUFFERS)`.

Источники: [PostGIS Spatial Index FAQ](https://postgis.net/documentation/faq/spatial-indexes/), [PostGIS: Using Spatial Indexes](https://postgis.net/docs/using_postgis_query.html).

#### 6.2.7. Ограничения и цена выбора PostGIS

- Нужны установка и администрирование PostgreSQL/PostGIS, резервное копирование, обновления и настройка индексов.
- Нужно осознанно выбрать CRS и тип `geometry`/`geography`; неправильная система координат приводит к неверным результатам, даже если SQL-запрос успешно выполняется.
- Некоторые операции с очень сложными полигонами могут быть дорогими по CPU и памяти.
- Пространственный индекс ускоряет поиск кандидатов, но не делает все геометрические операции мгновенными.
- Ремонт геометрии может менять тип и структуру результата, поэтому нужна проверка после `ST_MakeValid`.
- Для выдачи веб-карте огромного массива вершин и features всё равно может понадобиться упрощение или тайлинг.

Для проекта, где есть совместный доступ, регулярный импорт OSM, сложные пространственные запросы и бизнес-логика, эти издержки обычно оправданы.

### 6.3. SpatiaLite — пространственные функции для SQLite

**SpatiaLite** — расширение SQLite, добавляющее пространственные типы, функции, метаданные и индексы. Фактически это вариант пространственной базы данных в одном SQLite-файле, без отдельного сервера PostgreSQL.

Основные возможности:

- хранение геометрии в SQLite;
- функции импорта/экспорта геометрии и форматов: `GeomFromGeoJSON`, `AsGeoJSON`, WKT/WKB-функции;
- пространственные отношения: `ST_Intersects`, `ST_Contains`, `ST_Covers` и другие;
- геометрические операции и преобразование координат (при наличии соответствующих библиотек сборки);
- RTree-индексы через `CreateSpatialIndex`;
- работа с базой через GIS-инструменты, в частности QGIS.

Пример функций в документации SpatiaLite 5.1.0: `GeomFromGeoJSON(...)`, `AsGeoJSON(...)`, `CreateSpatialIndex(table, column)`, а также реализации пространственных предикатов. У ряда продвинутых функций есть зависимости от версий GEOS, PROJ и RTTOPO, поэтому доступность конкретного алгоритма определяется сборкой установленной библиотеки.

Преимущества:

- один переносимый файл;
- удобно для автономного приложения, настольной ГИС, прототипа и небольшого локального набора данных;
- не нужно разворачивать отдельный сервер;
- можно использовать SQL и пространственные индексы.

Ограничения:

- это embedded/file database, а не серверная СУБД, рассчитанная на ту же модель параллельной нагрузки и администрирования, что PostgreSQL;
- для работы пространственных функций клиент должен загрузить совместимую библиотеку SpatiaLite;
- возможности и доступность отдельных функций зависят от сборки и версий зависимостей;
- для крупного постоянно обновляемого набора OSM и нескольких одновременных пользователей чаще удобнее PostGIS.

Источники: [SpatiaLite SQL functions reference, v5.1.0](https://www.gaia-gis.it/gaia-sins/spatialite-sql-latest.html), [SpatiaLite Cookbook](https://www.gaia-gis.it/gaia-sins/spatialite-cookbook/index.html) (сам сайт предупреждает, что старый cookbook больше не поддерживается; используйте его как вводный материал), [SQLite R*Tree module](https://www.sqlite.org/rtree.html).

### 6.4. GeoPackage (GPKG) — переносимая пространственная база в одном файле

**GeoPackage** — открытый стандарт OGC, основанный на SQLite. Это не просто файл GeoJSON: контейнер может хранить векторные объекты, атрибуты, матрицы растровых/картографических тайлов, метаданные и расширения.

Основные возможности:

- один файл `.gpkg`;
- стандартизованная схема метаданных и пространственных таблиц;
- поддержка стандартных геометрий `Point`, `LineString`, `Polygon`, multipart-типов и `GeometryCollection`;
- хранение систем координат;
- стандартное расширение для R-tree пространственных индексов;
- хранение в одном контейнере векторных данных и тайлов растровой карты;
- широкая поддержка в GIS-инструментах и GDAL.

Преимущества:

- переносимость и хорошая совместимость между настольными ГИС;
- удобен для обмена большими наборами слоёв, когда один GeoJSON становится неудобен;
- можно использовать офлайн и передавать одним файлом;
- в одном контейнере доступны и векторные слои, и тайлы.

Ограничения:

- это файл SQLite, а не замена полноценной серверной СУБД для высококонкурентной многопользовательской системы;
- сам стандарт контейнера не превращает любой GIS-клиент в мощный движок топологической обработки — набор SQL-функций зависит от подключённого расширения (например, SpatiaLite) или внешнего инструмента;
- индексация и расширения должны поддерживаться читающим ПО.

Когда выбирать: передавать слои в QGIS, работать с полевыми/мобильными данными, хранить локальный кэш, архивировать тематические наборы, собирать проект в один файл.

Источники: [OGC GeoPackage Standard](https://www.geopackage.org/spec/), [OGC: GeoPackage overview](https://www.ogc.org/standards/geopackage/), [GDAL GeoPackage driver](https://gdal.org/en/stable/drivers/vector/gpkg.html).

### 6.5. MongoDB — геопространственные запросы в документной БД

MongoDB позволяет хранить GeoJSON-объекты внутри BSON-документов и создавать геопространственный индекс `2dsphere`.

Возможности `2dsphere`:

- запросы о геометриях в пределах заданной области;
- поиск ближайших объектов и запросы по расстоянию;
- пространственные пересечения и другие поддерживаемые геопространственные условия;
- индексация GeoJSON-объектов для сферической модели Земли.

Преимущества:

- естественно хранить геометрию рядом с вложенными JSON-подобными атрибутами;
- хорошо подходит, если основная модель приложения уже документная;
- есть встроенные геопространственные индексы и запросы близости.

Ограничения и оговорки:

- `2dsphere` — это прежде всего механизм геопространственного индексирования и запросов в документной БД, а не полный аналог набора пространственных операций PostGIS;
- набор операций и правила поддержки GeoJSON нужно сверять с используемой версией MongoDB;
- если нужен интенсивный полигональный overlay, топологическая чистка, сложная GIS-аналитика и стандартные пространственные SQL-паттерны, PostGIS обычно естественнее;
- координаты для `2dsphere` должны соблюдать допустимые диапазоны долготы и широты.

Когда выбирать: документно-ориентированный сервис, где нужны прежде всего поиск объектов по области и близости, а не сложное редактирование и наложение геометрий.

Источники: [MongoDB: Geospatial Queries](https://www.mongodb.com/docs/manual/geospatial-queries/), [MongoDB: 2dsphere Indexes](https://www.mongodb.com/docs/manual/core/indexes/index-types/geospatial/2dsphere/).

### 6.6. MySQL Spatial — геометрии в MySQL

MySQL поддерживает пространственные типы и ряд функций для геометрий: построение `Point`, `LineString`, `Polygon` и multipart-типов, преобразования GeoJSON/WKB/WKT, измерения и предикаты вроде `ST_Contains`, `ST_Intersects`, `ST_Area`, `ST_Buffer`.

Преимущество — возможность использовать геометрию в уже существующей инфраструктуре MySQL. Но список функций, индексация, поведение CRS и доступность конкретных геометрических операций зависят от версии MySQL и движка таблиц. Если пространственная аналитика является центральной частью проекта, PostGIS обычно предлагает более привычный и обширный GIS-инструментарий. Это не означает, что MySQL не может решать вашу задачу — нужно составить список реальных операций и проверить их поддержку на целевой версии.

Источники: [MySQL 8.4: Spatial Function Reference](https://dev.mysql.com/doc/refman/8.4/en/spatial-function-reference.html), [MySQL: Spatial Data Types](https://dev.mysql.com/doc/refman/8.4/en/spatial-type-overview.html).

| Решение | Тип решения | Подходит лучше всего для | Индексы / пространственные запросы | Главные ограничения |
|---|---|---|---|---|
| **PostGIS** | PostgreSQL extension / серверная БД | Центральное хранилище, совместная работа, OSM-импорт, аналитика | GiST, множество SQL-функций, геометрия и geography | Сложнее администрировать, чем локальный файл |
| **SpatiaLite** | SQLite extension | Локальная пространственная БД, desktop/offline | RTree, SQL-функции, GEOS/PROJ при наличии | Зависит от расширения; не серверная платформа уровня Postgres |
| **GeoPackage** | Стандартизованный SQLite-контейнер | Переносимые GIS-слои, обмен и офлайн | RTree extension; аналитика зависит от клиентского стека | Файл, не полноценная серверная пространственная платформа |
| **MongoDB** | Документная БД | JSON-документы плюс geo-query и proximity search | `2dsphere` | Не полный GIS overlay-движок |
| **MySQL Spatial** | Пространственные функции MySQL | Проекты на существующем MySQL | Spatial indexes и встроенные функции | Сверять функциональность и ограничения нужной версии |
| **GeoJSON** | Формат обмена | API и клиентская карта | Пространственного индекса нет в самом формате | Не база, не система транзакций, большие файлы многословны |

**Моя рекомендация:** если вы только начинаете и хотите серьёзно обрабатывать полигоны OSM, изучайте PostGIS в первую очередь. GeoPackage полезно освоить как переносимый файловый формат, а GeoJSON — как формат API/выдачи в браузер.

## 7. Библиотеки обработки и инструменты преобразования

Важно отличать хранилища из предыдущего раздела от библиотек: библиотека может читать файл и выполнять операции в памяти, но не обязательно является долговременным хранилищем.

### 7.1. GDAL/OGR

**GDAL** — библиотека и набор программ для работы с растровыми и векторными геоданными; для вектора используется абстракция OGR Simple Features.

Что полезно для вашей задачи:

- чтение/запись GeoJSON;
- импорт OSM XML и PBF (OSM driver);
- конвертация между GeoJSON, GeoPackage, Shapefile, PostGIS и другими форматами;
- фильтрация по пространственному охвату и атрибутам;
- перепроецирование;
- упрощение геометрий;
- запуск `MakeValid` во время обработки;
- объединение или разбиение слоёв при конвертации.

Пример конвертации GeoJSON в GeoPackage с перепроецированием в EPSG:25833:

```bash
ogr2ogr \
  -f GPKG output.gpkg input.geojson \
  -t_srs EPSG:25833 \
  -nln areas
```

Пример упрощения с допуском в единицах исходной CRS:

```bash
ogr2ogr -f GeoJSON simplified.geojson input.geojson \
  -simplify 0.5
```

**Важно:** `-simplify` использует единицы геопривязки исходного слоя. Если входной GeoJSON в градусах (WGS 84), `0.5` — это полградуса, а не полметра. Для метрического допуска сначала перепроецируйте данные в подходящую метрическую CRS. Упрощение сохраняет топологию отдельной геометрии, но не гарантирует сохранение топологических отношений всего слоя между соседними полигонами.

Для небольших OSM-выгрузок GDAL OSM driver удобен. Для импорта всей планеты или больших региональных выгрузок документация GDAL рекомендует использовать специализированный `osm2pgsql`.

Источники: [GDAL: ogr2ogr](https://gdal.org/en/stable/programs/ogr2ogr.html), [GDAL GeoJSON driver](https://gdal.org/en/stable/drivers/vector/geojson.html), [GDAL OSM driver](https://gdal.org/en/stable/drivers/vector/osm.html).

### 7.2. Shapely (Python)

**Shapely** — Python-библиотека для геометрических операций, использующая GEOS. Она позволяет работать с объектами `Point`, `LineString`, `Polygon`, `MultiPolygon`, коллекциями геометрий и выполнять геометрические операции в памяти.

Типичные функции и задачи:

- создание геометрий из координат, WKT, WKB или GeoJSON-подобных структур;
- `.area`, `.length`, `.bounds`;
- `.is_valid`, `.is_simple`;
- `.intersection()`, `.union()`, `.difference()`, `.buffer()`;
- `.contains()`, `.covers()`, `.intersects()`;
- `make_valid` для восстановления некоторых невалидных геометрий;
- `STRtree` для поиска геометрий по пространственным ограничениям.

Пример:

```python
from shapely import Polygon, Point, make_valid

area = Polygon([
    (13.40, 52.50),
    (13.41, 52.50),
    (13.41, 52.51),
    (13.40, 52.51),
    (13.40, 52.50),
])

probe = Point(13.405, 52.505)

print(area.is_valid)       # валидность геометрии
print(area.contains(probe))
print(area.area)            # в единицах координатной плоскости
```

Ограничения и важные особенности:

- Shapely — библиотека обработки в памяти, а не база данных;
- геометрические объекты Shapely неизменяемы: операция возвращает новую геометрию;
- обычные геометрические вычисления выполняются в плоскости XY; Z-координата может храниться, но не участвует в большинстве планарных аналитических операций;
- Shapely сам по себе не выполняет автоматическое преобразование CRS: для перепроецирования обычно используют `pyproj` или GeoPandas;
- `STRtree` в Shapely 2.x — индекс только для чтения: он строится по переданному набору геометрий и не поддерживает добавление/удаление объектов после создания;
- результат запроса по дереву может быть основан на пересечении bounding boxes; при необходимости требуется точный геометрический predicate.

Источники: [Shapely User Manual](https://shapely.readthedocs.io/en/stable/manual.html), [Shapely Geometry Types](https://shapely.readthedocs.io/en/stable/geometry.html), [Shapely STRtree](https://shapely.readthedocs.io/en/stable/strtree.html).

### 7.3. GeoPandas (Python)

**GeoPandas** расширяет pandas структурами для геометрических данных. В `GeoDataFrame` обычные атрибуты хранятся как столбцы, а один столбец назначается активной геометрией.

Полезные операции:

- `read_file()` — чтение из GeoJSON, GeoPackage и других поддерживаемых форматов;
- `to_file()` / `to_json()` — запись и выдача GeoJSON;
- `set_crs()` — назначить CRS без преобразования координат;
- `to_crs()` — реально перепроецировать координаты;
- `sjoin()` и `sjoin_nearest()` — пространственные соединения таблиц;
- `overlay()` — intersection, union, difference, identity и symmetric difference между слоями;
- `clip()` — обрезка геометрий по маске;
- `dissolve()` — объединение геометрий внутри групп;
- `explode()` — разделить multipart-геометрию на строки с отдельными компонентами;
- `.sindex` — пространственный индекс;
- `to_postgis()` — загрузка в PostGIS.

Пример загрузки набора в PostGIS:

```python
import geopandas as gpd
from sqlalchemy import create_engine

areas = gpd.read_file("areas.geojson")

# Назначайте CRS только если она достоверно известна.
# Если вход GeoJSON соответствует RFC 7946, это WGS 84.
areas = areas.set_crs("EPSG:4326", allow_override=True)

# Для измерений/буферов подберите подходящую метрическую CRS.
areas_metric = areas.to_crs("EPSG:25833")

engine = create_engine("postgresql+psycopg://user:password@localhost:5432/gis")
areas_metric.to_postgis("areas_metric", engine, if_exists="replace", index=False)
```

Осторожно: не используйте `set_crs` как замену перепроецированию. `set_crs` назначает метку системе координат; `to_crs` меняет координаты. Пример выше предполагает, что исходный GeoJSON действительно RFC 7946. Для долговременного хранения в PostGIS, если выходной слой должен быть RFC 7946 GeoJSON, при экспорте затем преобразуйте геометрию в WGS 84.

GeoPandas очень удобен для аналитики и сценариев обработки, но для большого потока запросов/пользователей не обязательно переносить всю серверную обработку из PostGIS в Python.

Источники: [GeoPandas User Guide](https://geopandas.org/en/stable/docs/user_guide.html), [GeoDataFrame API](https://geopandas.org/en/stable/docs/reference/geodataframe.html), [to_postgis](https://geopandas.org/en/stable/docs/reference/api/geopandas.GeoDataFrame.to_postgis.html), [overlay](https://geopandas.org/en/stable/docs/reference/api/geopandas.overlay.html).

### 7.4. Leaflet и MapLibre GL JS — отображение на карте

**Leaflet** — популярная JavaScript-библиотека для интерактивных веб-карт. Она умеет создавать GeoJSON-слои, стилизовать их по `properties`, фильтровать features, добавлять всплывающие окна и обработчики событий.

Пример:

```javascript
fetch("/api/areas.geojson")
  .then((response) => response.json())
  .then((geojson) => {
    L.geoJSON(geojson, {
      style: (feature) => ({
        color: "#2673b8",
        weight: 2,
        fillOpacity: 0.25
      }),
      onEachFeature: (feature, layer) => {
        const name = feature.properties?.name ?? "Без названия";
        layer.bindPopup(name);
      }
    }).addTo(map);
  });
```

Источники: [Leaflet: Using GeoJSON](https://leafletjs.com/examples/geojson/), [Leaflet API Reference](https://leafletjs.com/reference.html).

**MapLibre GL JS** также поддерживает GeoJSON source и позволяет передавать GeoJSON объект или URL. Внутри GeoJSON source данные разбиваются на тайлы для отображения. Это важно: свойства GeoJSON, которые не могут быть представлены в формате векторных тайлов, могут не сохраниться в отрисованных тайлах и связанных событиях. Если важны все исходные свойства, храните их отдельно или помещайте нужные данные в поддерживаемые feature properties.

Источники: [MapLibre: GeoJSONSource](https://maplibre.org/maplibre-gl-js/docs/API/classes/GeoJSONSource/), [MapLibre Style Specification: Sources](https://maplibre.org/maplibre-style-spec/sources/).

**Ключевое различие:** Leaflet и MapLibre показывают геометрию и дают инструменты взаимодействия с ней на карте; они не заменяют PostGIS или полноценный движок топологической обработки.

## 8. Практический пример: типовой цикл данных OSM → PostGIS → GeoJSON → карта

### Шаг 1. Получить исходные OSM-данные

Для теста достаточно небольшого PBF-экстракта нужного региона. Для выборок по тегам можно использовать Overpass API. Для большого/регулярно обновляемого импорта стоит использовать региональные PBF-выгрузки и `osm2pgsql`.

Не забывайте, что Overpass `out:json` — это формат ответа OSM API, а не GeoJSON. Убедитесь, что конвертер действительно собирает геометрии multipolygon relation из `outer`/`inner` участников.

Источники: [Overpass QL](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL), [osm2pgsql](https://osm2pgsql.org/doc/manual.html), [GDAL OSM driver](https://gdal.org/en/stable/drivers/vector/osm.html).

### Шаг 2. Импортировать в PostGIS

Для крупного OSM набора используйте `osm2pgsql` и Flex Output. Настройте собственные таблицы: например, отдельные таблицы для площадей, линейных объектов и точек. Не пытайтесь помещать всё в один столбец фиксированного типа `MultiPolygon`.

В зависимости от предметной задачи полезно разделять:

- площади — `geometry(MultiPolygon, 4326)` или подходящая метрическая CRS;
- линейные объекты — `geometry(MultiLineString, 4326)` / `geometry(LineString, 4326)`;
- точки — `geometry(Point, 4326)`;
- исходные OSM tags — `jsonb`;
- id и тип источника — отдельные колонки.

### Шаг 3. Проверить систему координат, тип и валидность

Примеры:

```sql
-- Найти объекты с некорректной геометрией
SELECT id, ST_IsValidReason(geom)
FROM osm_areas
WHERE NOT ST_IsValid(geom);

-- Посмотреть реальные типы
SELECT ST_GeometryType(geom), COUNT(*)
FROM osm_areas
GROUP BY ST_GeometryType(geom);

-- Проверить SRID
SELECT ST_SRID(geom), COUNT(*)
FROM osm_areas
GROUP BY ST_SRID(geom);
```

После импорта можно аккуратно выполнить исправление в отдельной staging-таблице, а не перезаписывать единственную копию исходных данных. Результат `ST_MakeValid` нужно перепроверить на тип, количество частей и смысловую корректность.

### Шаг 4. Выполнить пространственный запрос

Например, найти объекты площади, пересекающие заданную область:

```sql
SELECT id, osm_type, osm_id, tags, geom
FROM osm_areas
WHERE ST_Intersects(
    geom,
    ST_SetSRID(ST_MakeEnvelope(13.35, 52.48, 13.45, 52.55), 4326)
);
```

Найти участки, содержащие заданную точку:

```sql
SELECT id, tags
FROM osm_areas
WHERE ST_Covers(
    geom,
    ST_SetSRID(ST_Point(13.405, 52.505), 4326)
);
```

Для расстояния в метрах не используйте геометрию 4326 с радиусом в метрах. Для этого преобразуйте геометрию в подходящую метрическую проекцию или используйте поддерживаемую геодезическую функцию с `geography`.

### Шаг 5. Подготовить результат для веб-карты

- отобрать только нужные объекты и свойства;
- преобразовать геометрию в WGS 84 / CRS84;
- при необходимости упростить геометрию с допуском в осмысленных единицах;
- проверить валидность после преобразований;
- сериализовать как FeatureCollection;
- передавать с правильным MIME type `application/geo+json` и корректными CORS/cache-настройками, если API этого требует.

Пример принципа экспорта в PostGIS:

```sql
SELECT ST_AsGeoJSON(ST_Transform(geom, 4326))
FROM osm_areas
WHERE ST_Intersects(
    geom,
    ST_Transform(
      ST_SetSRID(ST_MakeEnvelope(13.35, 52.48, 13.45, 52.55), 4326),
      ST_SRID(geom)
    )
);
```

В реальном API лучше собрать полноценные Feature с нужными `properties`, а не возвращать отдельную строку GeoJSON на каждый объект без оболочки.

### Шаг 6. Отобразить поверх базовой карты

Клиентская библиотека получает GeoJSON и рисует его как отдельный слой поверх выбранного базового слоя. Базовая карта и ваш слой — разные источники: наличие тайлов OpenStreetMap не означает, что ваши GeoJSON-полигоны автоматически хранятся в OSM.

Для десятков/сотен простых features GeoJSON обычно удобен. Для очень больших наборов геометрий лучше подготовить векторные тайлы по масштабу карты, а не загружать все координаты и все объекты в браузер сразу.

Источники: [RFC 7946, Media Type](https://www.rfc-editor.org/rfc/rfc7946.html#section-12), [Leaflet GeoJSON tutorial](https://leafletjs.com/examples/geojson/), [MapLibre GeoJSONSource](https://maplibre.org/maplibre-gl-js/docs/API/classes/GeoJSONSource/).

## 9. Дополнительные темы, которые особенно важны для полигонов

### 9.1. CRS: хранение, измерения и карта

Вам, вероятно, придётся использовать не одну систему координат на всех этапах:

- **GeoJSON/API:** WGS 84 / CRS84, координаты `[lon, lat]`;
- **OSM:** географические координаты WGS 84;
- **расчёты площади/длины/буферов:** часто локальная проекция в метрах, например подходящая UTM-зона для территории исследования или официальная национальная проекция;
- **визуализация веб-карты:** многие базовые карты используют Web Mercator, но GeoJSON-данные обычно передаются в lon/lat и затем проецируются рендерером.

Для района Берлина может быть уместна UTM-зона 33N (например, EPSG:25833), но систему нужно выбирать по географическому охвату и методике проекта, а не по одному этому примеру.

**`ST_SetSRID` не преобразует координаты. `ST_Transform` преобразует.** Это одна из самых распространённых причин пространственных ошибок.

Источники: [RFC 7946, CRS](https://www.rfc-editor.org/rfc/rfc7946.html#section-4), [PostGIS ST_Transform](https://postgis.net/docs/ST_Transform.html), [GeoPandas: Projections](https://geopandas.org/en/stable/docs/user_guide/projections.html).

### 9.2. Точность, упрощение и топология

Упрощение сокращает количество вершин и размер данных. Но у полигонов есть две разные задачи:

1. сохранить форму каждого объекта;
2. сохранить согласованность соседних объектов между собой.

Операция упрощения с сохранением топологии отдельного полигона не обязательно гарантирует, что после независимого упрощения двух соседних полигонов их общая граница останется одинаковой. В результате могут появиться щели или наложения. Для кадастровых, административных и иных покрывающих территорию слоёв это может быть критично.

Практические рекомендации:

- не упрощайте мастер-геометрию без необходимости;
- создавайте отдельные генерализованные копии для разных масштабов;
- для слоёв с общими границами используйте топологически согласованную обработку;
- проверяйте результат после округления координат и преобразования CRS;
- не используйте градусный допуск как метрический.

Источники: [GDAL ogr2ogr — simplify](https://gdal.org/en/stable/programs/ogr2ogr.html), [RFC 7946 — Coordinate Precision](https://www.rfc-editor.org/rfc/rfc7946.html#section-11.2), [PostGIS Reference](https://postgis.net/docs/reference.html).

### 9.3. GeometryCollection — применять осознанно

`GeometryCollection` позволяет упаковать в одну геометрию элементы разных типов: например, точку, линию и полигон. Однако RFC рекомендует избегать вложенных коллекций и не использовать `GeometryCollection`, если достаточно `MultiPoint`, `MultiLineString` или `MultiPolygon`.

Для вашего сценария лучше не складывать дорожную линию и полигон лесного массива в одну коллекцию, если у них разный смысл, атрибуты или жизненный цикл. Обычно это разные `Feature` в одной `FeatureCollection` или разные слои/таблицы.

Источник: [RFC 7946, GeometryCollection](https://www.rfc-editor.org/rfc/rfc7946.html#section-3.1.8).

### 9.4. Если нужно редактировать исходную OSM-карту

Экспортированный GeoJSON не равен готовому набору изменений для OSM. GeoJSON представляет собранную геометрию; OSM API работает с элементами и отношениями, которые имеют собственные идентификаторы, версии, участников, теги и историю изменений.

Например, GeoJSON `MultiPolygon` после импорта из OSM может быть собран из нескольких `outer` Ways и `inner` Ways. Чтобы корректно отправить изменения обратно в OSM, недостаточно просто заменить координаты GeoJSON: нужно корректно изменить или создать Ways, Nodes и Relations, сохранить их связи и роли, проверить правила тегирования и выполнить загрузку через предусмотренный OSM-процесс редактирования.

Поэтому для отображения и собственного анализа используйте GeoJSON/PostGIS; для изменения самой базы OSM работайте через инструменты редактирования и модель OSM, не теряя связи исходных элементов.

Источники: [OSM Elements](https://wiki.openstreetmap.org/wiki/Elements), [OSM Relation](https://wiki.openstreetmap.org/wiki/Relation), [OSM Multipolygon](https://wiki.openstreetmap.org/wiki/Relation:multipolygon).

### 9.5. Производительность: большие GeoJSON и векторные тайлы

GeoJSON удобен, но для очень больших слоёв не всегда эффективен:

- JSON повторяет имена полей и имеет текстовую запись координат;
- клиент должен загрузить и разобрать документ;
- сложные геометрии содержат много вершин;
- при обновлении всего источника может передаваться большой объём данных.

Варианты оптимизации:

- запросы по bbox/территории, а не выдача всего слоя;
- фильтрация объектов на сервере;
- упрощённые геометрии для мелких масштабов;
- gzip/brotli сжатие HTTP-ответа;
- кэширование;
- векторные тайлы (MVT) для крупных и масштабируемых карт;
- отдельные слои по типам геометрии и тематике.

MapLibre указывает, что GeoJSON-источник тайлится внутри рендерера и что URL-источник предпочтительнее встроенного объекта для больших файлов. Это полезная подсказка, но не означает, что один очень большой GeoJSON всегда будет производительным — объём нужно измерять на реальном устройстве и наборе данных.

Источники: [RFC 7946, Coordinate Precision](https://www.rfc-editor.org/rfc/rfc7946.html#section-11.2), [MapLibre GeoJSONSource](https://maplibre.org/maplibre-gl-js/docs/API/classes/GeoJSONSource/).

### 9.6. Топология и граф дорог — не одно и то же, что геометрия

`LineString` описывает форму линии, но не определяет автоматически, как линия соединяется с другими линиями в графе дорог. Две линии могут визуально соприкасаться координатами, но не иметь общего узла/топологической связи в исходных данных; и наоборот, небольшие различия координат могут мешать соединению в вычислительной модели.

Если цель включает маршрутизацию, связность дорожной сети, повороты и ограничения, одной коллекции LineString недостаточно. Сохраняйте идентификаторы исходных OSM узлов и Ways или используйте специализированную сетевую модель и движки маршрутизации. Геометрический `ST_Intersects` отвечает на вопрос о пространственном пересечении, а не о допустимости проезда между двумя дорогами.

Источники: [OSM Elements](https://wiki.openstreetmap.org/wiki/Elements), [OSM Relation](https://wiki.openstreetmap.org/wiki/Relation), [OGC Simple Feature Access](https://www.ogc.org/standards/sfa/).

## 10. Что изучать в первую очередь

Рекомендуемая последовательность освоения:

1. **RFC 7946, разделы 3–5:** структура Geometry/Feature/FeatureCollection, координаты, Polygon, MultiPolygon, bbox. Это базовый контракт формата.
2. **OGC Simple Feature Access:** модель геометрий и понятия топологической валидности.
3. **PostGIS Getting Started / Data Management / Spatial Queries:** создание пространственных таблиц, CRS, GiST, предикаты и операции.
4. **OSM Elements + Multipolygon:** понимание исходной OSM-модели и сборка сложных площадей.
5. **osm2pgsql Flex Output:** загрузка OSM в собственную схему PostGIS.
6. **GDAL/OGR + GeoPandas/Shapely:** пакетные преобразования и Python-обработка.
7. **Leaflet или MapLibre:** отображение подготовленного GeoJSON поверх базовой карты.

Для заявленной задачи я бы начал с небольшого эксперимента: взять ограниченную OSM PBF-выгрузку, загрузить площадные объекты через `osm2pgsql` в PostGIS, проверить `ST_IsValid`, создать GiST-индекс, сделать выборку `ST_Intersects` по тестовому bbox и отдать результат как `FeatureCollection` в Leaflet/MapLibre.

## Заключение

Для геометрий `Polygon`, `MultiPolygon` и `LineString` GeoJSON — простой и широко поддерживаемый способ передать данные между сервером и веб-картой. Но при работе с OpenStreetMap нужно учитывать, что OSM хранит не готовые GeoJSON-объекты, а Nodes, Ways и Relations с тегами и ролями. Особенно это важно для multipolygon relation: её участники сначала должны быть собраны в корректные кольца и компоненты полигонов.

Для серьёзного хранения и обработки рекомендован PostGIS: типизированные geometry-колонки, CRS, индексы и богатые пространственные функции позволяют выполнять основную аналитику на стороне БД. GeoPackage/SpatiaLite полезны в автономных сценариях, Shapely/GeoPandas — в Python-конвейере, GDAL/OGR — для преобразования данных, Leaflet/MapLibre — для отображения. Наиболее надёжная схема — сохранять исходные OSM-идентификаторы и теги, отдельно контролировать валидность геометрии, выполнять измерения в подходящей CRS и только на границе API преобразовывать результат в RFC 7946 GeoJSON.
