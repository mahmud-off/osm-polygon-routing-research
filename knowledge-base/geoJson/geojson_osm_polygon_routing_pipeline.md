# Пайплайн применения пользовательских полигонов к OSM для маршрутизации

**Практическое проектирование исследовательского стенда: PostGIS + Valhalla / openrouteservice / OSRM / GraphHopper**  
**Дата актуализации источников:** 7 ноября 2026 г.

---

## 1. Резюме и рекомендуемый подход

Задача состоит не просто в том, чтобы нарисовать полигоны поверх OpenStreetMap, а в том, чтобы изменить множество доступных или предпочтительных дорожных рёбер при расчёте маршрута.

Для этого нужно разделять четыре сущности:

1. **Исходная OSM-карта** — PBF-файл с узлами, линиями и отношениями (`node`, `way`, `relation`).
2. **Входные зоны** — пользовательские полигоны из ZIP-архива. Это независимый набор геоданных, а не объекты OSM.
3. **Дорожный граф маршрутизатора** — производная структура, которую конкретный движок строит из OSM и собственных правил профиля.
4. **Политика применения зоны** — что делать с дорожными рёбрами, попавшими в полигон: полностью запретить, повысить стоимость, снизить скорость, разрешить только отдельным профилям и т. п.

**Главная рекомендация для первого стенда:** оставить оригинальный PBF неизменным, хранить и нормализовать полигоны в PostGIS, сначала проверить request-time исключение зон в Valhalla и ORS, а затем реализовать пространственное сопоставление «полигон → OSM-сегменты» и подключить OSRM/GraphHopper.

Такой порядок позволит быстро получить рабочий baseline, не смешивая ошибки геометрии, особенности модели OSM и особенности конкретного роутера.

### 1.1. Что именно сравнивать

Полезно сразу завести три экспериментальных класса:

| Класс | Где применяется полигон | Нужно перестраивать routing graph? | Примеры |
|---|---|---:|---|
| A. Runtime avoid area | В запросе маршрутизации | Нет, если движок поддерживает эту функцию | Valhalla `exclude_polygons`, ORS `avoid_polygons` |
| B. Runtime cost overlay | В вычислении веса рёбер во время запроса | Зависит от движка и формата оверлея | Valhalla `linear_cost_factors`, GraphHopper Custom Model Areas |
| C. Build-time graph modification | При импорте/подготовке графа | Да | OSRM Lua profile, модифицированный OSM PBF, импортируемые атрибуты рёбер |

Класс A — самый быстрый способ получить демонстрационный результат. Классы B и C нужны для более тонкого управления стоимостью, большого числа зон, фиксированных сценариев или движков без универсального polygon-параметра в API.

## 2. Перед реализацией: определить семантику полигона

Один и тот же `Polygon` может означать совершенно разные вещи. До написания кода зафиксируйте `effect` каждой зоны.

| Эффект | Семантика | Как это отражать в маршрутизаторе |
|---|---|---|
| `hard_avoid` | Нельзя использовать дорожные рёбра, пересекающие зону | Ребро исключается из поиска пути |
| `soft_avoid` | Проезд нежелателен, но допустим | Вес ребра увеличивается на коэффициент или штраф |
| `speed_limit` | Внутри зоны нужно ехать медленнее | Меняется скорость/время ребра |
| `profile_specific` | Ограничение действует только для определённого транспорта | Разные правила для car/truck/bike/foot |
| `time_window` | Ограничение действует в заданный интервал времени | Временная логика или отдельная версия графа |
| `allow_only` | Внутри зоны разрешены только явно заданные дороги/типы | Сначала исключить всё, затем явно разрешить выбранные рёбра |

Для первой версии рекомендую реализовать только два режима:

- `hard_avoid` — строгий запрет;
- `soft_avoid` — штраф за проезд.

Остальные режимы можно добавить после того, как будут корректно работать геометрическое пересечение, маршрутизация и тестирование.

### 2.1. Что означает «дорога попадает в полигон»

Нужно выбрать правило пространственного сопоставления. Это не техническая мелочь, а часть бизнес-семантики.

1. **Любое касание:** ребро помечается, если линия хотя бы в одной точке пересекает полигон (`ST_Intersects`). При таком правиле касание границы тоже считается пересечением.
2. **Ненулевая длина внутри:** учитывается только длина участка линии, лежащего внутри полигона. Можно задать порог в метрах, например исключать сегмент, только если внутри зоны находится более `X` метров.
3. **Доля сегмента внутри:** применять эффект, если доля длины сегмента внутри полигона превышает порог, например 20% или 50%.
4. **Полностью внутри:** сегмент затрагивается, только если целиком лежит в зоне (`ST_CoveredBy` / соответствующая проверка покрытия).
5. **Буфер вокруг полигона:** сначала расширить полигон на заданное расстояние, затем проверять пересечения. Буфер должен строиться в подходящей метрической проекции, а не в градусах EPSG:4326.

Для строгой зоны запрета обычно начинают с `ST_Intersects`, но обязательно тестируют касание границы, туннели/мосты и малые полигоны. Для «штрафа за нахождение внутри территории» лучше измерять долю/длину дорожного сегмента внутри зоны.

**Важное различие:** полигон может означать либо запрет на нахождение дорожной линии внутри него, либо запрет только на пересечение границы зоны. Для дорожного графа это не одно и то же. Зафиксируйте, что именно проверяется.

## 3. OpenStreetMap: что является объектом сопоставления

OSM не хранит дороги как готовые `LineString` GeoJSON-объекты. Базовая модель состоит из:

- `node` — точка с координатами;
- `way` — упорядоченная последовательность ссылок на узлы; из неё строится линия или граница площади;
- `relation` — набор узлов, линий и/или других отношений с ролями, задающий логическую связь между объектами.

Дорожный объект обычно представлен `way` с тегом `highway=*`. Но для маршрутизации одного `way` недостаточно: необходимо учитывать порядок его узлов, доступность по направлениям, ограничения доступа, поворотные ограничения, мосты/тоннели, паромы и другие теги.

### 3.1. Почему `way` — не всегда подходящая единица блокировки

Один OSM way может проходить несколько километров и пересекать несколько зон. Если отметить весь way как запрещённый при пересечении хотя бы одной зоны, можно убрать из маршрута и длинные участки дороги, географически не попадающие в зону.

Практически полезно различать уровни:

- **OSM way** — объект исходных данных;
- **OSM segment** — отрезок между двумя последовательными OSM nodes внутри way;
- **routing edge** — ребро графа конкретного движка между его узлами/точками разбиения. Границы routing edge могут отличаться от исходного OSM way и от сегментов OSM.

Для независимого от движка анализа удобно сначала работать с сегментами «между соседними OSM nodes», сохраняя `osm_way_id`, `from_node_id`, `to_node_id`. После этого нужно отдельно проверить, как движок переносит атрибуты на свои рёбра.

### 3.2. Мосты, тоннели и уровни

Простое двумерное `ST_Intersects(road_line, polygon)` не понимает высоту дорожной линии. Например, автомобильный мост может геометрически пересекать полигон парка, расположенного под мостом. Если бизнес-правило должно блокировать только дороги на уровне земли, нужно учитывать OSM-теги `bridge`, `tunnel`, `layer`, а там, где это поддерживается движком, уровни/этажность графа.

Это особенно важно для плотных городских сетей, развязок и многоуровневых дорог.

### 3.3. OSM multipolygon relation — не то же самое, что GeoJSON MultiPolygon

`MultiPolygon` — тип геометрии. OSM `type=multipolygon` — отношение, из которого геометрия площади собирается из member ways с ролями `outer` и `inner`. Входные полигоны из пользовательского ZIP не обязаны соответствовать OSM-отношениям; их не нужно превращать в OSM multipolygon relation, чтобы использовать в маршрутизации.

### 4.2. Valhalla

**Самый подходящий кандидат для первого теста исключаемых зон.** В официальном Route API есть `exclude_polygons`: можно передать кольца полигонов, и дороги/рёбра, пересекающие их, будут исключены во время поиска пути. Есть и вариант с `FeatureCollection`; у объектов могут присутствовать свойства `levels`, ограничивающие применение исключения определёнными уровнями рёбер.

Документация: [Valhalla Route API — Other request options](https://valhalla.github.io/valhalla/api/route/api-reference/).

Преимущества:

- не требуется менять исходный PBF;
- зоны можно передавать на каждый запрос отдельно;
- можно тестировать несколько полигонов в одном сценарии;
- `levels` полезен для некоторых многоуровневых дорожных ситуаций;
- `linear_cost_factors` позволяет сопоставлять LineString с дорожными рёбрами и применять коэффициент стоимости.

Ограничения и проверки:

- это исключение рёбер, а не универсальная геометрическая обрезка дорог по границе полигона;
- документация описывает внешние кольца; если входные полигоны имеют отверстия, проверьте, сохраняется ли семантика `inner rings` в вашем пути передачи данных;
- если начало или конец маршрута находится внутри запрещённой области, поведение нужно проверить отдельно;
- проверить, что именно считается «пересекающим» ребром на узком полигоне, касании границы и коротком сегменте;
- исключение может сделать маршрут недостижимым, и это ожидаемый результат для некоторых сценариев.

**Пример структуры запроса (псевдо-шаблон):**

```json
{
  "locations": [
    { "lat": 55.75, "lon": 37.61 },
    { "lat": 55.80, "lon": 37.70 }
  ],
  "costing": "auto",
  "exclude_polygons": [
    [
      [37.60, 55.74],
      [37.63, 55.74],
      [37.63, 55.77],
      [37.60, 55.77],
      [37.60, 55.74]
    ]
  ]
}
```

Формат вложенности массивов следует сверять с версией Valhalla, закреплённой в стенде; API также описывает альтернативный вариант с `FeatureCollection`. Не делайте собственный сериализатор без тестов на один полигон, несколько полигонов и MultiPolygon.

Для мягкого эффекта изучите `linear_cost_factors`: это не то же самое, что исключение территории. Там фактор применяется к рёбрам, которые движок сопоставляет с заданной линейной геометрией.

### 4.3. openrouteservice (ORS)

ORS предоставляет request option `options.avoid_polygons`, принимающий GeoJSON `Polygon` или `MultiPolygon`.

Документация: [ORS Backend — Routing Options](https://giscience.github.io/openrouteservice/api-reference/endpoints/directions/routing-options).

Пример запроса:

```http
POST /ors/v2/directions/driving-car/geojson
Content-Type: application/json
```

```json
{
  "coordinates": [
    [37.61, 55.75],
    [37.70, 55.80]
  ],
  "options": {
    "avoid_polygons": {
      "type": "MultiPolygon",
      "coordinates": [
        [
          [
            [37.60, 55.74],
            [37.63, 55.74],
            [37.63, 55.77],
            [37.60, 55.77],
            [37.60, 55.74]
          ]
        ]
      ]
    }
  }
}
```

Преимущества:

- формат входа непосредственно соответствует GeoJSON;
- `Polygon` и `MultiPolygon` документированы явно;
- удобно проверять разные наборы зон без перестройки графа;
- есть варианты профилей для авто, грузового транспорта, велосипеда, пешехода и инвалидной коляски (в зависимости от версии и конфигурации).

Ограничения:

- `avoid_polygons` — это жёсткое избегание площадей, а не произвольная система правил с приоритетами для каждой зоны;
- для большого числа сложных полигонов нужно исследовать размер HTTP-запроса, время расчёта и ограничения конфигурации;
- не переносите лимиты публичного hosted API на свой self-hosted экземпляр: проверяйте именно ту версию/конфигурацию, которую разворачиваете;
- необходимо проверять старт/финиш внутри зоны, отверстия в полигонах, пересечения границ и невозможность маршрута.

ORS можно развернуть локально на собственном PBF. Официальное руководство Docker описывает подключение пользовательского `.osm.pbf` через `source_file` и пересборку графа через `BUILD_GRAPHS=True`.

Документация: [Running openrouteservice with Docker](https://giscience.github.io/openrouteservice/run-instance/running-with-docker), [Input data](https://giscience.github.io/openrouteservice/run-instance/data).

### 4.4. OSRM

OSRM интересен для сравнения build-time подхода и стоимости на уровне дорожных сегментов.

В стандартном API есть параметр `exclude`, например `exclude=motorway`. Но это не произвольная геометрия: классы должны быть объявлены и назначены Lua-профилем во время извлечения OSM-данных.

Документация:

- [OSRM HTTP API](https://project-osrm.org/docs/v5.24.0/api/);
- [OSRM Profiles](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/profiles.md).

В Lua-профиле можно:

- в `process_way` определить доступность way и его атрибуты;
- установить `forward_classes` / `backward_classes` для way;
- объявить поддерживаемые `classes` и комбинации `excludable` в `setup`;
- затем исключать отмеченные классы в HTTP-запросе через `exclude=your_class`.

У этого есть важная особенность: класс в `process_way` относится ко всему OSM way. Если длинный way только частично пересекает полигон, можно случайно исключить весь way.

Для более точной обработки существует `process_segment`. Он вызывается для каждого отрезка между двумя соседними OSM nodes. В нём доступны координаты `source` и `target`, длина и возможность изменять `weight` и `duration`. Для гарантированного вызова по сегментам нужно включить `force_split_edges = true` в настройках профиля.

**Что это позволяет сделать:**

- вычислить заранее, какие пары соседних OSM nodes затрагивают полигоны;
- в `process_segment` сопоставить сегмент с внешним набором данных по координатам и увеличить его routing weight;
- таким образом исследовать `soft_avoid` на уровне OSM node-to-node сегментов.

**Чего это не даёт напрямую:**

- `process_segment` документирует изменение `weight` и `duration`, но не предоставляет отдельного поля `access=false` или `segment_class`, аналогичного атрибутам `process_way`;
- нет штатного API-параметра, куда можно положить произвольный GeoJSON-полигон на каждый route request;
- для гарантированного hard block части длинной дороги потребуется дополнительное решение: разбить геометрию на пригодные для блокировки OSM ways/сегменты и назначить им класс/недоступность при импорте либо изменить способ формирования графа.

**Практический маршрут для OSRM:**

1. Получить список сегментов OSM между соседними nodes.
2. Сопоставить их с зонами в PostGIS.
3. Для сценария создать атрибуты или модифицированный PBF/профиль.
4. Выполнить `osrm-extract` и, в зависимости от алгоритма, `osrm-partition` + `osrm-customize` (MLD) либо `osrm-contract` (CH).
5. Маршрутизировать через отдельный инстанс для данного сценария или использовать query-time `exclude` для заранее заданного класса.

Это хороший эксперимент для понимания различия между «геометрия в запросе» и «атрибуты рёбер, зашитые в graph build».

### 4.5. GraphHopper как дополнительный кандидат

GraphHopper Core поддерживает Custom Model Areas: в `areas` передаётся GeoJSON `FeatureCollection`, а в условиях модели доступны переменные вида `in_areaId`. Через них можно изменять `speed` или `priority` рёбер, расположенных в области.

Документация: [GraphHopper Custom Models — areas](https://github.com/graphhopper/graphhopper/blob/master/docs/core/custom-models.md).

Для MultiPolygon лучше предварительно разложить его на несколько отдельных Polygon features с разными `id`, если используемая версия следует текущему описанию Custom Model Areas: в документации указано, что feature должен иметь геометрию `Polygon`.

Это полезно для эксперимента с мягким штрафом:

- `speed` меняет не только вес, но и расчётное время;
- `priority` меняет предпочтительность/вес, не меняя фактическое расчётное время.

GraphHopper стоит включить в стенд, если важны кастомные модели и произвольное изменение стоимостей по районам.

### 5.1. Состав компонентов

| Компонент | Для чего | Рекомендуемый инструмент |
|---|---|---|
| Загрузка ZIP | Распаковать и прочитать векторные слои | GDAL/OGR (`ogrinfo`, `ogr2ogr`) |
| Нормализация геометрии | CRS, валидность, приведение к Polygon/MultiPolygon | PostGIS, GEOS, PROJ |
| Чтение OSM | Извлечь дороги/сегменты с идентификаторами | PyOsmium/libosmium; при необходимости osm2pgsql |
| Spatial matching | Найти пересекающиеся сегменты/зоны | PostGIS + GiST |
| Сценарии | Хранить режимы, даты, коэффициенты, группы полигонов | PostgreSQL |
| Routing engines | Расчёт маршрутов | Docker-контейнеры Valhalla, ORS, OSRM, GraphHopper |
| Тесты и метрики | A/B сравнение | Python, pytest, GeoPandas/Shapely |
| Просмотр | Карта с зонами, дорогами и маршрутами | Leaflet или MapLibre GL JS |

### 5.2. Почему PostGIS нужен, даже если маршрутизатор принимает GeoJSON

PostGIS не обязателен для простейшего запроса в Valhalla/ORS. Но для исследовательского стенда он очень полезен:

- единое каноническое хранилище зон;
- проверка валидности и системы координат;
- сопоставление всех зон с OSM-сегментами;
- возможность диагностировать, почему конкретная дорога попала или не попала под ограничение;
- подготовка engine-specific данных для OSRM и GraphHopper;
- воспроизводимость сценариев и версий данных.

Хранить геометрию лучше в колонке PostGIS `geometry`, а не только в JSONB. GeoJSON можно формировать на границе API через `ST_AsGeoJSON`.

## 6. Пайплайн обработки входного ZIP

### Шаг 1. Инвентаризация архива

В ZIP может лежать Shapefile (`.shp`, `.shx`, `.dbf`, `.prj`), GeoPackage, GeoJSON или несколько слоёв. Не предполагайте, что все полигоны имеют одинаковую CRS и одинаковый тип геометрии.

Проверьте архив и метаданные слоя:

```bash
unzip -l zones.zip
ogrinfo -al -so /vsizip/$(pwd)/zones.zip
```

Для Shapefile важно наличие `.prj`. Если CRS не определена, не назначайте EPSG:4326 автоматически без подтверждения поставщика данных.

### Шаг 2. Импорт в PostGIS

Примерная схема:

```sql
CREATE TABLE input_zones (
    zone_id       bigserial PRIMARY KEY,
    source_name   text,
    source_id     text,
    effect        text NOT NULL DEFAULT 'hard_avoid',
    profile       text NOT NULL DEFAULT 'all',
    priority      integer NOT NULL DEFAULT 100,
    penalty       double precision,
    valid_from    timestamptz,
    valid_to      timestamptz,
    geom          geometry(MultiPolygon, 4326) NOT NULL
);

CREATE INDEX input_zones_geom_gix
    ON input_zones USING GIST (geom);
```

Импорт выполняется через `ogr2ogr`, например:

```bash
ogr2ogr \
  -f PostgreSQL \
  'PG:host=localhost dbname=routing user=postgres password=postgres' \
  /vsizip/$(pwd)/zones.zip \
  -nln staging_zones \
  -t_srs EPSG:4326
```

Команда примерная: точные имена слоя, параметры доступа, геометрическую колонку и исходный CRS нужно подставить по результату `ogrinfo`.

### Шаг 3. Проверка и нормализация

Минимальный контроль:

```sql
-- Проверка валидности
SELECT zone_id, ST_IsValid(geom), ST_IsValidReason(geom)
FROM input_zones
WHERE NOT ST_IsValid(geom);

-- Исправление невалидных геометрий и извлечение polygonal-компонент
UPDATE input_zones
SET geom = ST_Multi(
    ST_CollectionExtract(ST_MakeValid(geom), 3)
);

-- Нормализация направления колец
UPDATE input_zones
SET geom = ST_ForcePolygonCCW(geom);

-- Проверка результата
SELECT zone_id, GeometryType(geom), ST_SRID(geom), ST_IsValid(geom)
FROM input_zones;
```

Не выполняйте `UPDATE` поверх единственной исходной копии: лучше хранить `source_geom` отдельно и записывать результат в нормализованную таблицу/версию. `ST_MakeValid` может превратить Polygon в MultiPolygon или GeometryCollection; поэтому после исправления необходимо извлечь именно полигональные части и проверить, что результат не пуст.

**CRS:** для маршрутизаторов обычно требуется долгота/широта WGS 84 (EPSG:4326), но исходную CRS необходимо прочитать, а затем действительно преобразовать через `ST_Transform`. `ST_SetSRID` не преобразует координаты — он только назначает идентификатор системы координат.

### Шаг 4. Геометрическая подготовка

По необходимости:

- объединить дублирующиеся зоны одного сценария (`ST_UnaryUnion` / `ST_Union`);
- разбить чрезмерно сложные полигоны для ускорения пространственных запросов (`ST_Subdivide`);
- применить метрический буфер (`ST_Buffer`) в локальной проекции;
- сохранить исходную геометрию и подготовленную для routing engine геометрию отдельно;
- привести кольца к правильной ориентации для совместимости с RFC 7946 при экспорте GeoJSON.

## 7. Получение дорожных сегментов из OSM

### 7.1. Для POC не загружайте всю Россию в каждый цикл разработки

По странице Geofabrik для России `russia-latest.osm.pbf` содержит всю страну. На момент проверки страницы файл указан размером около 3.9 GB, а выгрузка включает данные по 4 ноября 2026 года. Для первого прототипа лучше выделить небольшой район вокруг тестовых зон, сохранив достаточный буфер для построения объездов.

Источник: [Geofabrik — Russian Federation](https://download.geofabrik.de/russia.html).

Пример извлечения локального участка:

```bash
osmium extract \
  --bbox 37.20,55.50,38.10,56.10 \
  --strategy smart \
  -o study-area.osm.pbf \
  russia-latest.osm.pbf
```

Координаты здесь условные — подставьте bbox вашего полигона тестирования. Вокруг тестовой зоны должен оставаться запас: если вырежете слишком маленький регион, маршрутизатор может не найти реальный объезд из-за обрезанных дорог на границе экстракта.

`osmium extract` также умеет получать область по полигону. По документации он не обрезает OSM-объекты по границе экстракта; для корректного включения зависимостей ways/relations используется соответствующая стратегия (`complete_ways` по умолчанию, `smart` — с дополнительной полнотой multipolygon relations).

Источник: [Osmium — osmium-extract](https://docs.osmcode.org/osmium/latest/osmium-extract.html).

### 7.2. Извлечение сегментов

Для пространственного сопоставления нужны линии между последовательными узлами каждого маршрутизируемого way. У каждой такой линии должны сохраняться:

- `osm_way_id`;
- `from_node_id`;
- `to_node_id`;
- координаты начала и конца;
- `highway` и релевантные теги доступа;
- `oneway`, `bridge`, `tunnel`, `layer` и другие важные свойства;
- профиль транспорта, для которого этот сегмент потенциально маршрутизируем.

Поскольку OSM-файл — последовательный поток объектов с ссылками между ними, для корректной геометрии ways требуется получить координаты их nodes. PyOsmium/libosmium подходит для потокового чтения крупных PBF. Для полноценной обработки отношений могут потребоваться несколько проходов или AreaManager.

Источники:

- [PyOsmium — First Steps / OSM data model](https://docs.osmcode.org/pyosmium/latest/user_manual/01-First-Steps/);
- [PyOsmium — Working with Geometries](https://docs.osmcode.org/pyosmium/latest/user_manual/03-Working-with-Geometries/);
- [PyOsmium — Area Building](https://docs.osmcode.org/pyosmium/latest/reference/Area/).

### 7.3. Таблица сегментов

Пример целевой таблицы:

```sql
CREATE TABLE osm_segments (
    segment_id    bigserial PRIMARY KEY,
    osm_way_id    bigint NOT NULL,
    from_node_id  bigint NOT NULL,
    to_node_id    bigint NOT NULL,
    highway       text,
    oneway        text,
    bridge        text,
    tunnel        text,
    layer         text,
    access        text,
    geom          geometry(LineString, 4326) NOT NULL
);

CREATE INDEX osm_segments_geom_gix
    ON osm_segments USING GIST (geom);

CREATE INDEX osm_segments_way_id_idx
    ON osm_segments (osm_way_id);
```

Данная таблица — аналитическое представление OSM, не полноценный routing graph. В дальнейшем нужно сопоставить её с атрибутами/рёбрами конкретного движка.

## 8. Пространственное сопоставление «полигон → дорожные сегменты» в PostGIS

### 8.1. Найти все сегменты, которые касаются зон

```sql
SELECT
    s.segment_id,
    s.osm_way_id,
    z.zone_id
FROM osm_segments AS s
JOIN input_zones AS z
  ON ST_Intersects(s.geom, z.geom);
```

`ST_Intersects` возвращает true, если геометрии имеют хотя бы одну общую точку. В функцию встроена проверка bounding box, которая может использовать пространственный индекс.

Источник: [PostGIS — ST_Intersects](https://postgis.net/docs/ST_Intersects.html).

### 8.2. Измерить длину сегмента внутри полигона

Длины `geometry` в EPSG:4326 измеряются в градусных единицах, поэтому для порогов в метрах нужно проецировать геометрию в подходящую локальную метрическую CRS.

Пример для локальной тестовой области (EPSG здесь условный; выберите подходящую проекцию для своего региона):

```sql
WITH intersections AS (
    SELECT
        s.segment_id,
        s.osm_way_id,
        z.zone_id,
        ST_Transform(s.geom, 32637) AS segment_m,
        ST_Transform(z.geom, 32637) AS zone_m
    FROM osm_segments s
    JOIN input_zones z
      ON ST_Intersects(s.geom, z.geom)
), measured AS (
    SELECT
        segment_id,
        osm_way_id,
        zone_id,
        ST_Length(segment_m) AS segment_length_m,
        ST_Length(ST_Intersection(segment_m, zone_m)) AS inside_length_m
    FROM intersections
)
SELECT *,
       inside_length_m / NULLIF(segment_length_m, 0) AS inside_ratio
FROM measured
WHERE inside_length_m > 0;
```

В запросе EPSG:32637 условно подходит только для соответствующей UTM-зоны. Для России нет одной универсальной метрической проекции, одинаково подходящей для всех регионов. Для national-scale обработки разбивайте расчёт по подходящим CRS/зонам либо тщательно проектируйте расчёт с `geography` и геодезическими операциями.

`ST_Intersection` возвращает геометрию пересечения, а `ST_Length` измеряет длину линейного результата. Для `geometry` единицы зависят от CRS; для `geography` длина возвращается в метрах.

Источники: [PostGIS — ST_Transform](https://postgis.net/docs/ST_Transform.html), [PostGIS — ST_Length](https://postgis.net/docs/ST_Length.html).

### 8.3. Правило сопоставления настраивается отдельно от запрета

Получив `inside_length_m` и `inside_ratio`, можно реализовать разные стратегии:

```sql
-- A. Любое пересечение, включая касание границы
ST_Intersects(segment_geom, zone_geom)

-- B. Реальная длина внутри выше порога
inside_length_m >= 5.0

-- C. Значительная часть сегмента находится внутри зоны
inside_ratio >= 0.25

-- D. Сегмент целиком покрыт полигоном
ST_CoveredBy(segment_geom, zone_geom)
```

Пороговые значения в примерах не являются универсальной рекомендацией — их нужно определить по смыслу входных зон и проверить на характерных дорогах.

### 8.4. Материализованная таблица соответствий

Для воспроизводимости лучше сохранять результат overlay, а не выполнять его заново при каждом route request.

```sql
CREATE TABLE zone_segment_match (
    scenario_id        text NOT NULL,
    zone_id            bigint NOT NULL,
    segment_id         bigint NOT NULL,
    osm_way_id         bigint NOT NULL,
    inside_length_m    double precision NOT NULL,
    inside_ratio       double precision NOT NULL,
    match_rule         text NOT NULL,
    profile            text NOT NULL,
    PRIMARY KEY (scenario_id, zone_id, segment_id, profile)
);
```

Так можно сравнивать разные правила сопоставления:

- `intersects_any`;
- `inside_length_gt_5m`;
- `inside_ratio_gt_25pct`;
- `buffered_10m`.

## 9. Точность: дорожный сегмент может пересекать границу посередине

Это один из главных технических вопросов всей задачи.

Представим, что между двумя OSM nodes есть отрезок длиной 80 метров, а полигон перекрывает только 4 метра этого отрезка. Если routing engine хранит/обрабатывает этот отрезок как одну неделимую единицу, то исключение всего edge приведёт к блокировке всех 80 метров, а не только 4 метров внутри зоны.

Варианты:

### Вариант A. Блокировать/штрафовать весь затронутый сегмент

Самый простой и часто достаточный для первого теста. Результат дискретен на уровне сегмента между соседними OSM nodes. Нужно измерять ложное расширение запрета: сколько длины дороги оказалось исключено сверх фактического пересечения полигона.

### Вариант B. Использовать встроенное сегментное поведение движка

OSRM `process_segment` работает с отрезками между соседними OSM nodes, а не обязательно с длинным исходным way целиком. Для каждой такой пары можно заранее оценить пересечение с полигоном и задать новый вес.

### Вариант C. Вставлять дополнительные узлы в точках пересечения дороги с границей полигона

Если нужна точность до границы зоны, можно в производном, приватном routing input добавить синтетические OSM nodes в точках пересечения и включить их в последовательность node references соответствующего way. Это разобьёт исходный дорожный отрезок на более короткие сегменты перед импортом в routing engine.

Такой процесс сложнее:

- нужен уникальный диапазон ID для синтетических узлов;
- нельзя нарушать исходные node-way references;
- нужно аккуратно обрабатывать way direction, tags и relations;
- нельзя выдавать изменённый файл за исходные OSM-данные;
- после преобразования нужно проверять топологию и поворотные ограничения.

Для MVP я бы **не делал split PBF**. Сначала нужно измерить, насколько грубая сегментация влияет на результаты. Если ошибки важны — реализовать точное разбиение как отдельный эксперимент.

## 10. Как хранить зоны и сценарии

Не привязывайте геометрию напрямую к одному маршрутизатору. Сделайте нейтральную модель сценария.

Пример сущностей:

```text
source_dataset
  └── dataset_version

zone_source
  └── zone_normalized

scenario
  ├── scenario_zone
  ├── matching_rule
  └── profile_policy

osm_snapshot
  └── osm_segments

scenario_zone_segment_match

routing_engine_build
  ├── engine_name
  ├── engine_version
  ├── osm_snapshot_id
  ├── profile_hash
  └── build_parameters

route_case
  ├── start_point
  ├── end_point
  ├── travel_profile
  └── baseline_result / modified_result
```

В `scenario_zone` имеет смысл хранить:

- `zone_id`;
- `scenario_id`;
- `effect` (`hard_avoid`, `soft_avoid` и т. п.);
- `penalty_factor` или `penalty_seconds`;
- `buffer_m`;
- список профилей транспорта;
- `valid_from`, `valid_to`;
- приоритет и правила разрешения конфликтов.

**Не смешивайте геометрию зоны с её политикой.** Одна геометрия должна допускать несколько сценариев: например, в одном тесте она запрещённая, в другом — просто нежелательная.

## 11. Методика экспериментов

Чтобы результат был научно сравнимым, для всех движков фиксируйте:

- один и тот же OSM snapshot (дата/хэш PBF);
- один и тот же регион экстракта;
- версию движка и Docker image digest/tag;
- транспортный профиль;
- одинаковые origin/destination;
- одинаковые полигоны, CRS и правила применения;
- одинаковые настройки маршрута настолько, насколько это поддерживают движки.

### 11.1. Обязательные тестовые сценарии

| № | Геометрический случай | Что проверяем |
|---:|---|---|
| 1 | Дорога целиком внутри Polygon | Ребро исключается/штрафуется |
| 2 | Дорога пересекает узкий Polygon | Корректность edge intersection |
| 3 | Дорога касается только границы | Семантика касания |
| 4 | Polygon содержит hole, дорога проходит в hole | Сохраняются ли отверстия |
| 5 | MultiPolygon из нескольких раздельных частей | Поддержка MultiPolygon |
| 6 | Дорога-мост над полигоном | Учитывается ли уровень/мост |
| 7 | Тоннель под полигоном | Не блокируется ли неверный уровень |
| 8 | One-way дорога | Не нарушаются ли направление и доступ |
| 9 | Старт или финиш внутри запретной зоны | Поведение snapping и route search |
| 10 | Зона закрывает все возможные дороги | Возвращает ли движок корректный no-route |
| 11 | Полигон у границы PBF extract | Не вызван ли no-route слишком маленьким extract |
| 12 | Пересекаются две зоны с разными правилами | Разрешение конфликтов и приоритетов |

### 11.2. Метрики

Для каждого теста записывать:

- `route_found`;
- `route_distance_m`;
- `route_duration_s`;
- `route_weight` (если API выдаёт);
- длину/долю маршрута, попадающую в запрещённые зоны;
- длину дорожных сегментов, исключённых/оштрафованных сверх фактической части внутри зоны;
- detour ratio = `modified_distance / baseline_distance`;
- изменение ETA;
- latency API;
- время импорта/построения графа;
- размер графа на диске и RAM при запуске;
- размер запроса с polygon payload;
- число найденных OSM-сегментов и число реально затронутых routing edges (если доступно).

Самая важная проверка для `hard_avoid`: итоговая геометрия маршрута не должна проходить по запрещённой части сети с учётом выбранной tolerance. Проверять только визуально недостаточно — нужно вычислять пересечение геометрии маршрута с зонами и/или с ожидаемым множеством запрещённых рёбер.

### 11.3. Визуальный отчёт

Для каждого кейса удобно показывать на карте:

- базовый маршрут серым;
- маршрут с применённой зоной другим цветом;
- полигон с прозрачной заливкой;
- затронутые дорожные сегменты отдельным слоем;
- точки старта и финиша;
- OSM way ID и, где возможно, ID/атрибут routing edge.

Это сильно упрощает отладку: можно увидеть, что ошибка вызвана полигоном, неправильной CRS, отсутствующим дорожным сегментом, мостом или особенностью графа.

## 12. Предлагаемый план реализации по итерациям

### Итерация 1 — быстро проверить саму идею

1. Выбрать небольшой регион с несколькими дорогами и альтернативными объездами.
2. Взять один актуальный PBF extract с достаточным буфером.
3. Поднять один Valhalla и один ORS на одном PBF.
4. Вручную подготовить несколько простых GeoJSON Polygon/MultiPolygon.
5. Получить базовые маршруты без зон.
6. Отправить те же запросы с `exclude_polygons` / `avoid_polygons`.
7. Сохранить JSON-ответы и сравнить геометрию/время/дистанцию.

**Результат:** подтверждённый baseline request-time обработки полигонов.

### Итерация 2 — универсальный GeoJSON/OSM preprocessing слой

1. Импортировать ZIP-зоны в PostGIS.
2. Нормализовать CRS и валидность.
3. Извлечь OSM ways и node-to-node segments.
4. Построить spatial join.
5. Сохранить `zone_segment_match` для разных matching rules.
6. Добавить QGIS/MapLibre/Leaflet-визуализацию совпадений.

**Результат:** можно независимо от маршрутизатора объяснить, какие дорожные части попадают в зоны.

### Итерация 3 — OSRM

1. Написать custom Lua profile.
2. Начать с way-level custom class и `exclude`.
3. Включить `force_split_edges` и попробовать `process_segment` для soft penalties.
4. Сравнить сегментную классификацию с PostGIS truth table.
5. При необходимости исследовать производный PBF с синтетическими узлами.

**Результат:** оценка того, насколько OSRM подходит для build-time polygon overlays.

### Итерация 4 — GraphHopper и расширенные эффекты

1. Передать зоны в `Custom Model Areas`.
2. Проверить speed penalty и priority penalty.
3. Проверить MultiPolygon после декомпозиции на Polygon features.
4. Сравнить hard avoid и soft avoid.

### Итерация 5 — масштабирование

Только после прохождения функциональных тестов переходить к большому региону/России, большим объёмам полигонов, batch processing и автоматическому обновлению OSM.

## 13. Важные инженерные ограничения и анти-паттерны

1. **Не изменять базовый PBF на месте.** Хранить оригинал и отдельный производный набор для каждого build-сценария.
2. **Не использовать EPSG:4326 для метрического буфера и длины.** Долгота/широта подходят для формата API, но не для плоской метрической арифметики.
3. **Не считать, что `way` равен routing edge.** У движка собственное разбиение графа.
4. **Не считать любое касание автоматически достаточным основанием для запрета.** Зафиксируйте boundary policy.
5. **Не забывать про мосты/тоннели/слои.** 2D-пересечение может быть ложным с точки зрения маршрутизации.
6. **Не сравнивать движки на разных PBF snapshots.** Версия карты — часть эксперимента.
7. **Не экстрагировать слишком маленький прямоугольник.** Иначе вы измеряете край экстракта, а не эффект полигона.
8. **Не хранить единственный результат `ST_MakeValid` без сохранения исходника.** Проверяйте результат после исправления.
9. **Не путать полигон отображения с полигоном routing constraint.** Карта может продолжать отображать дорогу под зоной, хотя роутер её избегает. Это нормально: map rendering и routing graph — независимые системы.
10. **Не предполагать поддержку всех GeoJSON-деталей каждым движком.** Отдельно протестируйте holes, MultiPolygon, Z/levels, пустые геометрии и размер запроса.

## 14. Итоговая рекомендация

Для вашего исследовательского стенда я бы выбрал следующую комбинацию:

- **PostGIS** — основное хранилище зон, версий, OSM-сегментов и результатов spatial matching;
- **PyOsmium/libosmium** — получение дорожных ways и node-to-node сегментов из PBF;
- **Valhalla + ORS** — первые два движка для немедленной проверки runtime-полигонов;
- **OSRM** — отдельная ветка экспериментов с build-time обработкой и стоимостью node-to-node сегментов;
- **GraphHopper** — дополнительный кандидат для Custom Model Areas и мягких штрафов;
- **Python + Shapely/GeoPandas + pytest** — автоматизация набора кейсов и анализ результатов;
- **Leaflet или MapLibre** — визуальное сравнение исходной/модифицированной маршрутизации.

Не нужно заранее решать, что все движки обязаны использовать один и тот же технический механизм. Для сравнения важнее иметь одну семантику зон и один набор входных тестов, а затем реализовать адаптер, наиболее естественный для каждого движка.

**Критерий успеха MVP:** на одном OSM snapshot можно воспроизводимо выполнить одинаковый набор пар A/B маршрутов без зон и с зонами, показать на карте изменённые маршруты, объяснить список затронутых дорожных сегментов и выгрузить таблицу метрик.

## Примечание о версиях
