# [**Werner — _GISCUP 2015: Notes on Routing with Polygonal Constraints_***](https://www.bgd.ed.tum.de/pdf/2015_giscup15_Werner.pdf)
1. **Постановка задачи:** Дан набор данных OpenStreetMap (около 100 000 линейных сегментов дорог в проекции Web Mercator EPSG:3857, точки поворотов и атрибуты скорости) и набор полигонов. Необходимо найти самый быстрый/короткий маршрут, который **не пересекает** внутреннюю область или границы этих полигонов.
2. **Анализ алгоритмов:**
    - _Дейкстра:_ Прост в реализации, служит отличным базовым уровнем (ground truth) для проверки корректности более сложных алгоритмов.
    - _A*:_ Направленный поиск, но на малых наборах данных и в проекции Web Mercator (где расчет расстояний нетривиален) может работать даже медленнее Дейкстры.
    - _ALT (A_, Landmarks, Triangle inequality): Использует заранее вычисленные расстояния до "ориентиров" (landmarks). Автор выбрал этот метод, так как предвычисленные данные остаются валидными даже при наличии ограничений (хотя их эффективность снижается).
    - _Иерархии (Highway/Contraction Hierarchies) и Edge Flags:_ Автор отмечает их главный недостаток для данной задачи: они требуют сложного и дорогого препроцессинга, который становится невалидным или даже вводящим в заблуждение при динамическом изменении графа (например, если полигон перекрывает основной мост, все предвычисленные "короткие пути" через него становятся бесполезными).
3. **Реализация:** Использованы C++, Boost Geometry и Boost Graph Library (BGL). Для быстрого поиска пересечений применен R*-tree (`boost::geometry::index::rtree`).
## Полезные выводы для вашей исследовательской задачи
- **Использование R_-деревьев:** Для эффективного сопоставления полигонов с ребрами графа автор настоятельно рекомендует использовать пространственные индексы, такие как **R*-tree**. Запрос вида `intersects(poly, road)` работает крайне быстро и позволяет избежать перебора всех ребер графа (O(N) превращается в O(log N)). Это прямой ответ на вопрос о «вычислительной эффективности» на этапе геометрического сопоставления.
- **Осторожность с проекциями:** Автор отмечает, что проекция Web Mercator (EPSG:3857), стандартная для OSM, искажает расстояния. При расчете эвристик (например, для A*) или длин пересечений это может привести к непредсказуемому влиянию на маршрутизацию. В вашем исследовании стоит сравнить, как разные проекции влияют на точность сопоставления и итоговый вес ребра.
- **Преимущество ALT (Landmarks):** Если вы применяете корректировки весов "на лету", алгоритмы, основанные на иерархиях (Contraction Hierarchies), потребуют дорогостоящего пересчета. ALT же использует неравенство треугольника для эвристик. Даже если вес ребра увеличивается (положительная корректировка) или уменьшается, нижние оценки расстояний, вычисленные на этапе препроцессинга, остаются математически корректными (валидными), что делает ALT одним из лучших кандидатов для баланса между скоростью и динамичностью.

# [**Werner et al. — _Finding the shortest path under polygonal obstacle constraints_***](https://www.researchgate.net/publication/312512912_Finding_the_shortest_path_under_polygonal_obstacle_constraints)
Статья **«Finding the shortest path under polygonal obstacle constraints»** (авторы Xu Yan и Dawei Liu) — это еще одна работа, посвященная задаче конкурса ACM SIGSPATIAL GIS Cup 2015. В отличие от предыдущей статьи Мартина Вернера, где использовались сложные пространственные индексы (R*-tree) и алгоритм ALT, здесь авторы фокусируются на классической реализации алгоритма **A*** и предлагают более простой, «наивный» подход к обработке полигональных ограничений.
**Основные тезисы статьи:**
1. **Алгоритмическая база:** Используется алгоритм A* с двумя типами эвристик: для поиска кратчайшего пути (евклидово расстояние) и для поиска быстрейшего пути (евклидово расстояние, деленное на максимальную скорость в сети).
2. **Метод обработки полигонов (Node-based filtering):** Вместо того чтобы проверять пересечение каждого _ребра_ (дороги) с полигоном, авторы проверяют только _вершины_ (узлы графа). С помощью алгоритма **Ray Casting (Even-Odd Rule)** они определяют, какие узлы находятся внутри полигона, и на самом старте работы алгоритма добавляют их в множество `CLOSED` (посещенных). Это фактически "выключает" эти узлы из поиска.
3. **Структуры данных:** Авторы провели интересное сравнение хранения графа в виде **индексных массивов** и **хэш-таблиц**. Результаты (Таблицы 2 и 3) показали, что хэш-таблицы обеспечивают примерно 10-кратный прирост скорости выполнения запросов по сравнению с массивами.
4. **Влияние на пространство поиска:** Эмпирически показано, что появление полигонального препятствия заставляет алгоритм A* исследовать значительно больше узлов (размер множеств `OPEN` и `CLOSED` возрастает в разы), прежде чем будет найден обходной путь.

Эта статья представляет огромную ценность для вашего исследования, так как предлагает **альтернативный (упрощенный) метод** работы с полигонами, который можно использовать в качестве **базового уровня (baseline)** для сравнения с более точными методами.

Вот что конкретно можно вынести для ответа на ваш исследовательский вопрос:

#### 1. Готовая гипотеза для сравнения: Node-based vs Edge-based Mapping

Ваша задача требует сравнить методы сопоставления полигонов с графом. Статья дает вам первый метод для сравнения:

- **Метод из статьи (Node-based / Точечный):** Мы проверяем только вершины графа. Если вершина попадает в полигон (с помощью быстрого Ray Casting), мы меняем вес всех инцидентных ей ребер или блокируем её.
    - _Плюсы:_ Высокая вычислительная эффективность (Ray Casting работает очень быстро).
    - _Минусы:_ Низкая точность. Длинное ребро может пересекать полигон, но если его концы (вершины) находятся снаружи, алгоритм из статьи этот полигон проигнорирует.
- **Продвинутый метод (Edge-based / Геометрический):** Проверка реального пересечения геометрии ребра (LineString) с границами полигона (как делал Вернер с помощью R*-tree).
    - _Плюсы:_ Высокая точность.
    - _Минусы:_ Вычислительно сложнее.
- **Для вашего исследования:** Вы можете замерить, насколько сильно упрощение (Node-based) искажает итоговый маршрут по сравнению с точным (Edge-based) при применении положительных и отрицательных весов.

# [**Dibbelt, Strasser, Wagner — _Customizable Contraction Hierarchies_***](https://dl.acm.org/doi/pdf/10.1145/73393.73421)
# 1. О чём статья
Статья посвящена задаче построения кратчайшего пути в **двумерной полигональной среде**, где пространство разбито на области с разными весами. Это классическая computational geometry / route planning работа, не про OpenStreetMap и не про дорожный граф как таковой, а про **непрерывное перемещение по плоскости с полигональными зонами разной стоимости**.
## 2.2. Главный практический вывод: нужно аккуратно переводить геометрию в граф

Статья показывает, что если среда содержит полигональные весовые зоны, то нельзя просто грубо назначить веса без учёта геометрии.

Для точного решения нужно построить такой граф, который содержит все потенциально оптимальные переходы между зонами.

В вашей задаче это означает:

> способ сопоставления полигонов рёбрам OSM напрямую влияет на точность, скорость и предсказуемость маршрутизации.

Например, если дорога только слегка касается штрафного полигона, а вы назначаете штраф всему ребру целиком, маршрут может измениться слишком сильно.

И наоборот, если длинное ребро частично проходит через полигон, а вы не учитываете долю пересечения, маршрут может получиться непредсказуемым.

---

## 2.3. Статья подсказывает несколько уровней точности сопоставления

На основе идеи критического графа можно выделить несколько практических методов для вашей задачи.

### Метод 1. Проверка вершин графа

Для каждой вершины OSM проверяется, попадает ли она внутрь полигона.

Если вершина внутри полигона, корректируются:

- сама вершина;
- инцидентные ей рёбра;
- или стоимость входа/выхода из вершины.

Плюсы:

- очень быстро;
- просто реализовать;
- дёшево для динамических обновлений.

Минусы:

- низкая геометрическая точность;
- длинное ребро может пересекать полигон, но его концы находятся снаружи, и корректировка не применится;
- возможна плохая предсказуемость маршрутов.

Аналог в статье: учет точек и вершин как событий, но для точного решения этого недостаточно.

---

### Метод 2. Бинарное пересечение ребра с полигоном

Проверяется:

text

`intersects(edge, polygon)`

Если ребро пересекает полигон, ему назначается корректировка.

Плюсы:

- проще, чем считать длину внутри полигона;
- быстрее, чем дробить ребро;
- хорошо работает для запретов или грубых штрафов.

Минусы:

- не учитывает, какая часть ребра находится внутри полигона;
- может сильно переоценивать влияние;
- маршрут может стать менее предсказуемым.

Пример:

text

`Длина ребра = 1000 м. Полигон задел только 10 м. Бинарный метод может оштрафовать все 1000 м.`

---

### Метод 3. Доля пересечения ребра с полигоном

Вычисляется длина части ребра внутри полигона:

text

`L_inside = length(edge ∩ polygon)`

Тогда корректировка может быть пропорциональна этой длине.

Например:

text

`f = L_inside / L_edge`

Варианты изменения стоимости:

#### аддитивный

text

`cost' = cost + penalty * f`

#### мультипликативный

text

`cost' = cost * (1 + penalty_factor * f)`

#### скоростной

text

`speed' = speed * (1 - discount_factor * f)`

Плюсы:

- гораздо точнее бинарного метода;
- влияние корректировки более пропорционально;
- хорошо подходит для положительных и отрицательных бизнес-весов;
- лучше объяснимая метрика.

Минусы:

- дороже вычислительно;
- нужно реально считать геометрические пересечения;
- при большом числе полигонов нужна пространственная индексация.

Этот метод ближе всего к логике статьи, где стоимость зависит от длины пути внутри области с определённым весом.

---

### Метод 4. Разбиение ребра в местах пересечения границ полигона

Это самый точный графовый подход.

Если ребро дороги пересекает границу полигона, в точки пересечения добавляются новые вершины графа. Ребро разбивается на участки:

text

`outside → inside → outside`

Каждый участок получает свой вес.

Плюсы:

- высокая точность;
- маршрутизатор реально видит, где начинается и заканчивается зона;
- можно назначать разные стоимости для входа, выхода и движения внутри;
- наиболее предсказуемое влияние на маршрут.

Минусы:

- увеличивается размер графа;
- дороже препроцессинг;
- сложнее динамически обновлять;
- нужно контролировать дубликаты вершин и топологию.

Именно этот подход концептуально ближе всего к идее **critical graph** из статьи: чтобы получить корректный путь, нужно включить в граф важные геометрические точки входа/выхода.

## 3. Итеративный роутинг как модель предсказуемого влияния

Итеративный роутинг в статье работает так:

1. Найти кратчайший путь с текущими весами.
2. Проверить, проходит ли путь через изменённые рёбра.
3. Если да — повторить запрос с учётом изменений.
4. Повторять, пока путь не стабилизируется.

**Применение к вашей задаче:** это готовая модель для оценки **предсказуемого влияния** корректировки. Если после применения полигона маршрут не изменился — корректировка не повлияла на результат. Если изменился — можно измерить, насколько. Это даёт метрику:
```text
влияние = изменился ли маршрут / насколько изменилась стоимость
```
